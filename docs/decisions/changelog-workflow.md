# CHANGELOG 维护规则

## 已确认决定

- 从现在起，每完成一个功能模块，都必须同步更新项目根目录的 `CHANGELOG.md`。
- `CHANGELOG.md` 更新属于功能交付的一部分，不能只改代码、不记变更。
- 如果模块完成时没有更新 `CHANGELOG.md`，该任务不算按 workflow 完成。

## 适用范围

- 新功能模块。
- 现有功能模块的重要增强、重构、行为变更、兼容性调整。
- 会影响用户能力、开发者接口、配置方式、调试方式或交付流程的模块级改动。

## 记录要求

- 写清模块名称和本次变化的用户可感知结果。
- 写清重要限制、兼容性影响、迁移提示或已知注意事项。
- 尽量聚焦“完成了什么能力”和“会如何影响使用”，不要只罗列零碎代码动作。

## 执行约定

- 功能模块完成后，在结束任务前更新 `CHANGELOG.md`。
- 同一次任务中的代码、文档、测试与 `CHANGELOG.md` 变更应一起提交审阅。
- 如果本次工作只是纯内部噪音清理，且没有模块级可见变化，可以不写新条目，但应能明确说明原因。
- 如果一个模块分多次交付，应在每次形成可验证增量时追加对应条目。

## 文件位置

- 统一使用仓库根目录 `CHANGELOG.md`。
- 需要补充更详细背景时，可在 `docs/decisions/` 或相关设计文档中展开，但 `CHANGELOG.md` 仍必须保留摘要条目。

## 通过标准

- 用户或协作者只看 `CHANGELOG.md`，就能知道最近交付了哪些模块能力。
- 每个已完成模块都能在 `CHANGELOG.md` 中找到对应记录。
