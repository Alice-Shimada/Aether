# Aether 当前值得保留的部分、可能需要更改的部分与最高优先级判断

> 状态：已完成  
> 生成日期：`2026-04-18`  
> 来源：综合 `cross-project-synthesis.zh-CN.md` 与 `question_reviews/2026-04-18-user-adaptation-memory-boundary/` 本轮复审结果  
> 目的：把“现在 Aether 哪些骨架值得保留、哪些地方值得更改、两边各自最高优先级是什么”整理成一份可直接用于后续设计讨论的正式短结论。

## 0. 先给结论

这轮全量审阅和专题复审之后，Aether 当前最不该推翻的，不是某个局部小机制，而是它已经形成的这套总体方向：

- 长期真源和运行时层分开；
- 用户自适应和更宽记忆不混成一个无边界共享池；
- 当前 session 的临时要求和长期习惯分开；
- 高影响长期内容保留用户确认权；
- 作用域、引用层、活跃集这些运行时边界已经开始成形。

同时，当前最突出的短板也已经很清楚：

> Aether 现在已经比较擅长“管理习惯”，但还不够擅长在每轮运行时稳定地“知道这个用户是谁、哪些信息必须默认带上、哪些信息只该按需回忆”。

如果只再往前收一层优先级，那就是：

- 最值得保留的一点：用户适配真源必须可审计、可纠错、可撤销。
- 最值得优先修改的一点：尽快补出一层小而稳定、总是带上的用户层。

## 1. 当前最值得保留的东西

### 1.1 三块架构本身值得保留

这里指的是：

- 独立习惯库真源；
- Aether 工作区引用层；
- session 暂存区。

这一点值得保留，因为它天然防止了几种常见混淆：

- 长期真源和运行时状态混在一起；
- 临时要求和长期规则混在一起；
- 用户信息、历史回忆、agent 经验混在一起。

外部项目虽然术语不同，但成熟样本普遍都在分：

- 长期真源；
- 当前运行时装配；
- 临时材料或短期回忆。

所以 Aether 先拆成三块，总体方向是对的。

### 1.2 confirmed habits 作为长期真源值得保留

这层的价值在于：

- 长期习惯有正式承载处；
- 系统不必每次都重新猜用户是谁；
- 后续纠错、删除、审计有稳定入口。

外部项目里的对应物虽然名字不同，但本质上都有相似角色：

- `USER.md`
- `user summary`
- `human block`
- 稳定 profile

这说明“长期用户事实应有正式真源”这件事本身没有问题。

### 1.3 proposal review / human-in-the-loop 值得保留

这是 Aether 和很多“自动学习你”的方案之间最重要的差别之一。

它值得保留，因为它保住了三件事：

- 用户知道系统为什么这样理解自己；
- 错误写入长期层后可以及时纠正；
- 高影响长期偏好不会轻易被一次偶发表达固化。

AI 当然可以继续承担很多工作：

- 自动提取候选；
- 合并重复项；
- 归纳范围；
- 生成建议文本。

但高影响长期习惯仍应以用户确认作为主结构。

### 1.4 session scratch 值得保留

这层解决的是非常真实的运行时问题：

- 用户刚在当前对话里提出的新要求，不一定该永久写入；
- 但系统又应该在当前 session 里先尊重它。

所以这层保住了一个重要边界：

- 当前先执行；
- 是否长期保留再说。

它比“立刻永久化”或“完全不记”都稳。

### 1.5 当前 session active set 值得保留

把“当前真正生效的内容”单独表达出来，这一点很重要。

也就是：

- imported confirmed habits；
- active scratch habits；

共同构成当前 session 的生效集合。

这个表达很有价值，因为它明确回答了：

- 当前到底哪些规则在生效；
- 它们来自哪里；
- 它们是不是临时的。

以后无论补稳定用户层、session recall、通用记忆层，都不应该丢掉这层表达。

### 1.6 多作用域 scope 值得保留

当前这套：

- `global`
- `subject`
- `initiative`
- `task_scope`
- `artifact`

不但不多余，反而说明 Aether 提前看到了外部项目里反复出现的问题：

- 不是所有长期信息都全局适用；
- 不是所有偏好都应该每次都带上；
- “长期有效”不等于“全场景生效”。

外部项目很多并没有 Aether 这么明确地表达作用域，所以这块更像“先进但还没完全用透”，而不是设计失误。

### 1.7 工作区层只存 refs 和轻量背景值得保留

`global_guidance / project_guidance / session binding` 这套思路有一个非常对的原则：

- 工作区层负责引用、缩范围、解释；
- 不复制长期真源正文。

这很重要，因为一旦工作区层也变成正文仓库，就容易出现：

- 同一条用户事实多处复制；
- 改错时不知道改哪处；
- 运行时层和真源层边界模糊。

### 1.8 “用户习惯真源先以用户侧证据为主”值得保留

这条边界现在仍然稳：

- 在用户自适应系统本身里，
- 长期用户习惯真源先以用户侧证据为主。

这不等于说 assistant 输出永远不能进入任何长期记忆。

它真正表达的是：

- 用户适配真源要更谨慎；
- 更宽通用记忆以后可以再放宽；
- 但不能把 assistant 文本直接等同于用户习惯证据。

### 1.9 “运行时装配层”和“长期真源层”分开值得保留

Aether 当前已经隐含地在做这件事，只是还没完全命名清楚。

这条值得保留，因为外部成熟路线普遍都在区分：

- 真源；
- 编译结果或视图；
- 当前 prompt / 当前上下文装配。

如果把三者压平，后面就会很难解释：

- 为什么这条信息这轮会进主回答；
- 它是长期规则、临时规则，还是一次检索命中。

### 1.10 “当前先把用户自适应和更宽记忆分开分析”值得保留

这轮复审反复说明：

- 用户自适应和记忆系统强相关；
- 但二者并不等价。

所以 Aether 当前没有把二者直接压成一个总词，这个谨慎态度是对的。

至少在下面这些层面，分开分析仍然有价值：

- 真源；
- 运行时装配；
- 删除和纠错；
- 作用域；
- 是否直接影响主回答行为。

### 1.11 “先治理，再放大自动化”这个方向值得保留

外部统一底座路线很强，但也更容易出现：

- 误写长期画像；
- 用户很难解释为什么系统这样判断；
- 后面想回滚时代价很大。

所以 Aether 当前先把治理、确认、作用域、真源做稳，再逐步扩大自动化，这个顺序值得保留。

### 1.12 “不要把项目知识、用户信息、agent 经验混写”值得保留

这条在 Aether 现有骨架里其实已经被提前照顾到了。

它很重要，因为跨项目反例已经说明：

- 项目知识记忆不等于用户记忆；
- 用户适配也不等于所有类型的长期记忆；
- agent 经验和用户偏好长期混写会污染解释边界。

## 2. 为什么这些点值得保留

把上面这些点合在一起看，Aether 当前真正有价值的地方在于：

- 它认真地区分了长期真源和运行时层；
- 它认真地区分了临时候选和正式习惯；
- 它认真地区分了适用范围；
- 它认真地给用户保留了确认权和纠错入口；
- 它没有急着把所有信息压进一个统一大池子。

所以当前主问题不是“骨架完全错了”，而是：

- 运行时用户层还不够清楚；
- session recall 还没单独站稳；
- 更宽记忆层还没明确接法；
- 运行时默认入口还不够稳定。

## 2.1 当前保留项里的最高优先级

如果只能在“值得保留”的点里选一个最高优先级，我会选：

> 用户适配真源必须可审计、可纠错、可撤销。

原因不是它技术上最复杂，而是它决定了 Aether 的产品底线。

这条一旦丢掉，会直接带来几类风险：

- 用户不知道系统为什么这样理解自己；
- 错误长期写入后很难修；
- 后面即使接入更强记忆能力，信任感也会下降；
- 用户会把系统看成“偷偷改写我的画像”，而不是“我能共同治理的长期助手”。

## 3. 当前可能需要更改的东西

### 3.1 缺少稳定用户层

这是当前最明显、也最值得优先改进的地方。

多数成熟样本都会再抽出一层：

- 很小；
- 很稳定；
- 默认常驻；
- 直接影响主回答行为；
- 不等于全部长期记忆。

而 Aether 当前虽然有：

- confirmed habits；
- scope；
- proposal；
- scratch；
- active set；

但还没有把“默认总是带上的稳定用户层”真正独立出来。

### 3.2 当前更像“习惯管理系统”，还不够像“稳定运行时用户系统”

现在的 Aether 更擅长：

- 提取候选习惯；
- 审核长期习惯；
- 管理作用域；
- 区分长期和临时。

但从运行时视角看，它还缺少一个特别直接的入口去回答：

- 这位用户最稳定的几条偏好是什么；
- 哪几条应该每轮默认带上；
- 哪些只该按需召回。

所以短板不是“不会存”，而是“默认怎么稳定地用”还不够清楚。

### 3.3 confirmed habits 和运行时默认入口之间还缺一个中间层

当前结构里已经有：

- 长期真源；
- 工作区引用层；
- 当前活跃集。

但还缺一个中间层，专门负责把长期真源压缩成：

- 小；
- 稳；
- 默认带上；
- 可直接影响主回答行为；

的运行时用户视图。

这个中间层可以是：

- `USER.md` 视图；
- `user summary` 视图；
- current context packet 的独立分区；
- confirmed habits 的编译结果。

### 3.4 session recall 还没有单独站稳

现在有三件事仍然容易被混谈：

- 过去聊过什么；
- 这个用户通常喜欢怎样被对待；
- 正式知识材料里写了什么。

如果 `session recall` 不单独成层，后面就容易出现：

- 某次历史对话被误当成长期用户习惯；
- 某条项目上下文被误当成正式真源；
- 运行时分不清自己是在“查用户画像”还是在“翻旧对话”。

### 3.5 稳定用户层和更宽记忆层的边界还不够清楚

这轮复审给出的稳定共识是：

- 稳定用户层应更小、更谨慎；
- 更宽记忆层可以更丰富；
- 二者在运行时强耦合，但不该是同一层对象。

而 Aether 当前还没有把这条边界正式表达清楚：

- 什么信息总要带上；
- 什么信息只按需召回；
- 什么信息根本不该直接影响主回答。

### 3.6 未来通用记忆不应先走“大共享池”路线

如果未来要接更宽通用记忆，更稳的方向是：

- 统一编排层；
- 分层真源；
- 分开治理；
- 运行时再组合。

不稳的方向则是先做一个把所有东西都丢进去的大池子，把：

- 用户稳定信息；
- 历史会话；
- assistant 输出；
- 任务材料；
- agent 经验；
- 环境事实；

全混在一起。

这样会直接带来：

- 存的时候边界不清；
- 用的时候解释不清；
- 改错和删除时责任不清。

### 3.7 主动召回值得单独设计

外部项目已经说明：

- “系统能搜索”
- 和
- “系统会在该回忆的时候主动把该回忆的东西带上”

不是一回事。

如果只靠模型临时判断是否去搜，就容易出现：

- 明明有材料，但没触发；
- 触发了，但太晚；
- 搜到了，但没有成为主回答前置条件。

所以后面需要单独回答：

- 哪些用户信息应在主回答前主动带上；
- 哪些历史对话值得预召回；
- 哪些材料只在需要时再检索。

### 3.8 时间变化和失效治理还不够清楚

这轮外部项目有一条很重要的提醒：

- 很多“记错用户”的问题，本质上不是检索差，而是时间建模差。

Aether 当前后续需要继续明确：

- 哪些偏好是长期的；
- 哪些只是近期状态；
- 偏好变化后旧值怎样失效；
- 是否保留历史轨迹；
- 纠正时是覆盖、撤销，还是标记旧事实失效。

### 3.9 assistant 输出进入长期层的边界还不够细

当前谨慎边界总体没问题，但下一步还需要继续细化：

- assistant 输出是不是永远不能进长期层；
- 如果不是，哪些类型可以进更宽通用记忆；
- 哪些类型绝不能直接进入用户适配真源；
- 任务结果、工具结果、系统观察与 assistant 文本是否要分开处理。

### 3.10 删除、纠正、追责的层边界还需要提前设计

如果未来层次继续增加，就不能只问“有没有删除功能”，还要问：

- 删除的是稳定用户层，还是通用记忆层；
- 改错改的是正式真源，还是运行时编译视图；
- 追责看哪一层的证据；
- 用户能否区分“删画像”和“删回忆”。

这类治理问题如果不提前分层，后面一扩能力就会变复杂。

### 3.11 讨论话题仍然有点混

当前 Aether 相关讨论里，至少有四件事常被放在一起说：

- 用户自适应；
- session recall；
- 通用记忆；
- 程序性技能层。

这会让很多设计问题看起来像一个问题，但其实不是。

所以接下来需要把这些问题拆开讨论，再在运行时组合。

### 3.12 下一步需要从“有没有层”转向“层之间如何编排”

这轮复审后，真正更重要的问题已经不是：

- 要不要某一层。

而是：

- 这层的真源是什么；
- 它的编译结果是什么；
- 它什么时候读；
- 它什么时候写；
- 它和别层冲突时谁优先；
- 哪些内容会直接影响主回答。

也就是说，Aether 现在该从“列层”转向“定义层间关系”。

## 3.1 当前可改项里的最高优先级

如果只能在“可以修改”的点里选一个最高优先级，我会选：

> 尽快补出一层小而稳定、总是带上的用户层。

原因很直接：

- 它最先影响每轮运行时体验；
- 它决定系统能否稳定知道“这个用户是谁”；
- 它能给后面的 session recall 和更宽记忆层提供装配锚点；
- 它比继续扩 scope、放宽证据来源、立刻接大记忆层都更基础。

换句话说，当前最核心的问题不是“不会存”，而是“默认怎么稳定地用”还不够清楚。

## 4. 当前最大架构问题

### 4.1 一句话版本

当前最大架构问题是：

> Aether 已经能比较认真地管理习惯，但还没有形成一层明确、稳定、低成本、总是带上的用户层，所以运行时仍偏依赖临时匹配，而不是稳定地把“这个用户是谁、长期该怎么对待他”压成一个小而强的默认入口。

### 4.2 这个问题不等于什么

它不等于：

- 当前三块架构错了；
- confirmed habits 不该有；
- scope 太多；
- proposal review 太重；
- session scratch 太复杂。

恰恰相反。

当前这些骨架大体都值得保留。

真正的问题是：

- 在这些骨架之上，
- 还缺一个“稳定用户层”的运行时落点。

## 5. 当前不应误判成“最大问题”的东西

这轮复审后，下面这些不应该被误判成当前最大的架构问题：

- `scope` 太多  
  更大的问题不是作用域太多，而是稳定用户层还没独立出来。

- proposal review 太保守  
  更大的问题不是 review 太重，而是还没有一个小而稳的用户层把高价值信息固定下来。

- session scratch 太复杂  
  scratch 反而是当前比较合理的部分，不是首要矛盾。

- 当前只看用户消息证据太窄  
  这确实是后面会继续扩展的边界，但现在还不是最核心的架构缺口。

## 6. 下一步最值得围绕什么继续讨论

后续如果继续围绕这份文档推进，最值得优先讨论的是：

1. Aether 的稳定用户层是否先做成一个 `USER.md` 视图，还是别的编译结果。
2. 这层是独立真源，还是 confirmed habits 的压缩结果。
3. 这层和 active scratch、confirmed habits、session recall、未来通用记忆之间的优先级。
4. 这层默认承载哪些内容，不应该承载哪些内容。
5. 这层的更新方式是自动提议、用户确认、手工编辑、还是周期性重写。
6. session recall 是否应单独成层，并与适配层明确分开。
7. 如果以后接更宽记忆层，assistant 输出、任务结果、环境事实分别怎样入层。
8. 纠错、删除、回滚、审计分别在哪一层发生。

## 7. 当前建议

基于这轮全量审阅与专题复审，当前最稳的路线不是推翻现有骨架，而是：

- 保留当前三块架构和 confirmed habits 主线；
- 保留 proposal review / human-in-the-loop；
- 尽快补一个稳定用户层；
- 把 session recall 单独站稳；
- 以后把更宽通用记忆层作为平行层继续接入；
- 让运行时装配逐步从“习惯管理系统”走向“稳定用户层 + 按需召回层 + 临时活跃层”的组合系统。
