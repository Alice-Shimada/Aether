# 沟通输出规则

## 已确认决定

- 从现在起，回答实现、排查、配置、接口或用法相关问题时，默认尽量给出具体代码示例，不只停留在概念描述。
- 如果存在更合适的代码片段、命令示例、配置片段、文件结构示例，应优先提供可直接参考的例子。
- 只有在问题纯属原则讨论、没有合理示例落点，或示例会造成误导时，才可以只讲概念。

## 适用范围

- 代码实现建议、重构建议、调试结论、配置说明、API 用法、脚本命令、测试写法、文档示例。
- 适用于 TypeScript、Bun、Shell、JSON、JSONC、YAML、Markdown 等本项目常见格式。

## 默认输出方式

- 先给结论，再给最小可用示例。
- 优先使用与当前仓库技术栈一致的示例，例如 TypeScript、Bun API、项目现有目录结构。
- 示例应尽量短、可读、可复制，并贴近当前问题场景，而不是给抽象伪代码。
- 如果需要说明取舍，可在示例后补一句原因，而不是只给原理不落地。

## 执行约定

- 解释代码修改建议时，默认附上关键片段或建议写法。
- 解释配置变更时，默认附上配置前后或目标配置示例。
- 解释调试路径时，默认附上日志命令、筛查命令、断言代码或诊断示例。
- 如果没有给出示例，应有明确原因，例如“该问题只有流程约束，没有合适代码落点”。

## 通过标准

- 用户看完回复后，应能直接拿示例开始改、查、配或验证，而不必再把概念二次翻译成代码。
- 示例应服务于当前结论，不为凑格式而添加无关片段。
