# IPK：用户风格画像与自适应助手系统（独立于 Piece 库）

这份文档记录一个新的重要架构判断：

- `piece` 库系统
- 用户风格画像与自适应助手系统

最好拆成两个相互协作、但职责不同的系统。

## 1. 核心结论

我认同这个方向：

> “长期知识 / 想法库” 和 “逐渐变得懂使用者的助手” 不应完全混成同一个系统。

原因是这两类信息在本质上不同。

### 1.1 `piece` 系统记录的是内容对象

它关心的是：

- 你想了什么
- 你知道什么
- 你讨论过什么
- 你卡在哪里
- 你做过什么项目

这些信息适合被结构化成：

- `piece.md`
- `meta.json`
- `surface.json`
- `links.json`

### 1.2 用户风格系统记录的是交互偏好与长期认知特征

它关心的是：

- 你喜欢什么样的解释
- 你不喜欢什么样的回答方式
- 你偏谨慎还是偏探索
- 你需要多高密度的论证
- 你在哪些情境下更喜欢严谨，在什么情况下更喜欢发散
- 你最近提出过哪些反复出现的风格性要求

这些信息往往不是一个独立内容对象，不适合直接变成普通 piece。

## 2. 为什么这两者应该拆开

如果不拆开，会出现几个问题。

### 2.1 容易把“内容”与“偏好”混淆

比如：

- “这次讨论中你提出了一个关于 RG 的想法”
- “你更喜欢先给直觉、再补论证”

这两者显然不是同一类东西。

前者是知识 / 想法内容。  
后者是交互偏好与回答策略信号。

### 2.2 用户风格信号往往不是显式存储行为

你说得很对：

- 用户不会每次都说“请记住我喜欢什么”
- 很多风格偏好是在长期交流里自然显现出来的
- 它们往往通过要求、纠正、抱怨、追问、满意/不满意反馈体现

所以这类信息不适合走“一键生成 piece 并入库”的流程。

### 2.3 如果每次会话都立即改写用户画像，系统会过度敏感

这也是你提得很准的一点。

如果系统每次会话都马上得出：

- “用户就是喜欢 X”
- “用户就是讨厌 Y”

那很容易出现：

- 被偶然情境带偏
- 把一次性的要求误判为长期偏好
- 用户画像来回抖动

所以这个系统不能是“瞬时记忆”，而应该是“证据积累 + 周期总结”。

## 3. 推荐架构：独立的 Profile / Policy 系统

我建议把这部分单独设计成一个系统，暂时可以叫：

- `profile` 系统
- 或 `adaptation` 系统

它至少分成两层。

### 3.1 `profile`

记录用户相对稳定的认知与偏好特征。

例如：

- 已掌握知识层级
- 理论语言偏好
- 数学细节需求
- 回答风格偏好
- 对直觉 / 证明 / 发散 / 保守 的偏向

### 3.2 `policy`

记录系统当前的互动策略。

例如：

- 这个用户通常喜欢先直觉后论证
- 但在研究型问题上应主动补更严谨的边界说明
- 最近系统观察到用户过度保守，可适度鼓励更开放探索

这两层必须分开，因为：

- `profile` 描述用户是什么样
- `policy` 描述系统准备怎么回应

## 4. 这个系统不该按“每次会话直接写死”来更新

我建议它采用三层更新机制。

## 5. 第一层：会话内即时信号抽取

每次会话结束后，系统可以自动分析这次交流里出现了哪些“风格信号”。

比如：

- 用户要求“讲得更严谨一点”
- 用户要求“不要上来就给我太抽象的形式主义”
- 用户表示“我更想看发散性的想法”
- 用户反复要求“先从我已经会的东西出发”

这些都可以被抽成事件，而不是直接改写长期 profile。

我建议这层只生成：

- `signals`

而不是直接改写稳定画像。

## 6. 第二层：信号积累

系统应把多次会话中的信号先累计起来。

例如：

- 最近 20 次会话里，有 8 次要求更严谨
- 最近 10 次研究讨论里，有 6 次希望保留更多发散
- 最近 15 次学习型会话里，多次要求从熟悉知识起步

这里最重要的是：

- 看趋势
- 看重复
- 看场景分布

而不是看某一次。

## 7. 第三层：周期性总结与画像更新

只有在积累了足够信号后，系统才对 profile / policy 做总结和更新。

我建议第一版至少支持两种触发方式。

### 7.1 自动周期更新

例如：

- 每 10 次会话
- 或每周
- 或最近信号变化足够大时

自动生成一次 profile 更新建议。

### 7.2 用户显式要求更新

例如用户说：

- “帮我总结最近的学习风格”
- “更新一下你对我表达偏好的理解”
- “总结一下最近我更喜欢怎样的回答方式”

这时系统可以主动生成一次新的画像总结。

## 8. 推荐的数据流：信号、总结、画像

为了避免系统过度敏感，我建议把这套数据流拆成三层对象。

### 8.1 `signals`

最小事件单位。

例如：

- `prefers_more_rigorous_argument`
- `dislikes_overly_abstract_opening`
- `wants_more_associative_exploration`

每个 signal 应该带：

- 来源会话
- 出现位置
- 证据片段
- 置信度
- 适用场景

### 8.2 `summaries`

对一段时间 signals 的总结。

例如：

- 最近一个月用户在研究型问题里明显更偏向高论证密度
- 在学习型问题里更强调从已有知识出发

### 8.3 `profile / policy`

最终持久化、在后续会话中会被使用的稳定层。

## 9. 这个系统应该记录什么，不记录什么

### 9.1 适合记录

- 回答风格偏好
- 解释顺序偏好
- 抽象层次偏好
- 证明密度偏好
- 对发散联想的接受度
- 常见不满意点
- 已知知识背景的高层画像

### 9.2 不适合过早固化

- 一次性情绪
- 一次性要求
- 很具体但只适用于某个问题的临时偏好
- 没有重复出现证据的弱信号

## 10. 我建议第一版先做“低敏感画像”

你提到“不能太敏感”，我非常同意。

所以我建议第一版故意克制，不要试图捕捉太多细粒度偏好，而是先记录更稳的几类。

例如：

- 解释风格偏好
- 论证密度偏好
- 已有知识起点偏好
- 发散 / 保守 倾向
- 学习型问题和研究型问题的风格差异

第一版不要急着做：

- 太细粒度的语气偏好
- 太短期的风格波动
- 过于心理化的画像判断

## 11. 推荐的更新策略

我建议 future system 至少遵守下面几条更新规则。

### 11.1 单次信号不能直接改写长期画像

任何长期画像都应来自多次证据。

### 11.2 风格结论必须带置信度

例如：

- 高置信度：多次重复出现
- 中置信度：在特定场景下重复出现
- 低置信度：仅有零散证据

### 11.3 风格偏好应尽量按场景存储

比如：

- 学习问题
- 研究问题
- 写作问题
- 复盘问题

因为用户在不同场景下很可能偏好不同。

### 11.4 允许系统提出“反向建议”

这很重要。

如果系统观察到：

- 用户长期过于谨慎
- 用户长期过于跳步
- 用户总是避开严格论证
- 用户总是压抑联想探索

那么系统应该能在 policy 层写出：

- 未来适度补更多论证
- 或适度鼓励更多探索

这能防止系统变成一个只会迎合的机器。

## 12. 这个系统如何在后续会话中使用

未来普通问答开始时，系统可以先读：

- 当前问题
- 当前 profile
- 当前 policy

然后决定：

- 回答时先从熟悉知识切入，还是先直接给结论
- 先讲直觉，还是先给证明框架
- 要不要主动补边界条件
- 要不要主动加一个发散可能性

这层不一定非要显式露出来，但它应在后台持续起作用。

## 13. 这个系统和 Piece 系统如何协作

它们应该是两个系统，但不是孤立的。

### 13.1 Piece 系统给它提供证据土壤

很多风格信号其实来自长期对话、长期讨论和长期 piece 生成中的反馈。

### 13.2 风格系统给 Piece 检索与回答提供调制

例如同样查 IPK，系统可以因为 profile 不同而：

- 选择更保守的检索路径
- 或选择更开放的联想路径
- 回答组织方式也不同

### 13.3 二者不能互相替代

- piece 系统不能取代用户画像系统
- 用户画像系统也不能取代知识与想法库

## 14. 推荐的第一版实现策略

如果以后真落代码，我建议先做一个非常克制的第一版。

### 14.1 第一步

每次会话结束后，抽取少量风格信号。

### 14.2 第二步

先只做信号积累，不直接更新 profile。

### 14.3 第三步

支持用户主动触发：

- “总结最近的风格和偏好”

### 14.4 第四步

在确认这类总结稳定后，再写入 profile / policy。

### 14.5 第五步

最后再让普通问答默认读取这套 profile / policy。

## 15. 当前最推荐的结论

结合你的想法，我现在最推荐的方向是：

1. `piece` 库继续作为内容系统
2. 新增一个独立的用户风格 / 自适应系统
3. 这个系统以“会话信号 -> 周期总结 -> 画像更新”为主链
4. 它默认低敏感，不因单次对话大幅改写用户画像
5. 它允许系统在理解用户的同时，保留适度纠偏能力

## 16. 一句话总结

未来真正“懂你的助理”不应只来自知识库，还应来自一个独立的、低敏感、可渐进更新的用户画像与互动策略系统。
