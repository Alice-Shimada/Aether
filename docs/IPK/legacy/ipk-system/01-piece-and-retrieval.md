# IPK：Piece、存储与分级检索设计草案

这份文档记录当前对 `piece`、底层存储、检索结构、联想结构和 skill 协作方式的初步设计。

它要解决的核心问题是：

- IPK 里未来可能有海量 `pieces`
- 不能靠传统关键词检索作为唯一入口
- AI 需要既能快速、准确地找到最需要的内容
- 又要保留自由联想和跨主题连接的能力
- 同时不能把太多正文直接塞进上下文，否则会慢、贵、且不准

## 1. 一个关键结论：Skill 不应该承载 Piece

这里要先明确一个非常重要的边界。

`piece` 不应该被做成 skill。

原因很简单：

- skill 适合承载“方法”
- piece 适合承载“内容”

更具体地说：

- skill 负责告诉 AI 如何检索、如何联想、如何总结、如何沿着知识结构继续深入
- piece 负责保存用户自己的想法、知识、经历、讨论结果、反思、计划

如果把大量 piece 直接做成 skill，会有几个问题：

- skill 数量会爆炸
- 系统提示词会变得巨大
- 每次会话都会暴露过多无关内容
- skill 的描述层会被“数据量”污染，失去作为工作流协议的清晰性

所以对 IPK 最合理的理解是：

- `IPK` 是一个数据层
- `Skill` 是一个工作流层
- `Tool / Query` 是一个执行层

也就是说，未来更理想的关系应该是：

1. skill 决定这次要用什么检索策略
2. 检索工具去读 IPK 的索引和局部内容
3. AI 再根据需要逐层深入到 piece 正文

## 2. 推荐的整体架构：表层索引 + 渐进披露 + Skill 协议

你刚才提到的方向其实是对的，我会把它明确命名成：

`表层索引 + 渐进披露 + Skill 协议`

这三层分别做不同的事。

### 2.1 表层索引

它不是正文，而是“让 AI 判断是否值得继续找下去”的低成本暴露层。

这一层应该尽量：

- 短
- 稳定
- 可结构化解析
- 足够表达 piece 的方向、价值、上下文和关系

### 2.2 渐进披露

AI 不应该一上来就读全文，而应该分层进入：

1. 先看总览
2. 再看候选
3. 再看局部摘要
4. 最后才读目标 piece 正文

这样可以把“检索准确性”和“上下文控制”同时做好。

### 2.3 Skill 协议

skill 负责规定：

- 什么时候先按项目找
- 什么时候先按概念找
- 什么时候先走时间线
- 什么时候要偏保守检索
- 什么时候允许更发散的联想扩展

所以 future skill 不应该是“一个个知识片段”，而应该是“几类查询和思考策略”。

## 3. Piece 应该作为统一最小单元

我仍然认为，用 `piece` 作为 IPK 的统一最小单元是最好的。

理由是：

- 它足够中性，不会预设内容一定是笔记、卡片、论文摘要还是日记
- 它允许未来出现很多不同类型
- 它适合做统一的索引和关系网络

但是 `piece` 不能只是“一个文件”这么简单。

更合理的理解是：

- `piece` 是统一对象
- 对象有类型
- 对象有多标签
- 对象有关系
- 对象有多层暴露面

## 4. Piece 的存储建议：物理分层，逻辑多维

你担心“所有 piece 都放在一个大文件夹里会不会太臃肿”，这个担心完全正确。

我不建议：

- 单一大平铺目录

我也不建议：

- 完全依赖目录树表达所有分类语义

最稳的做法是混合式：

- 物理存储按稳定维度分层
- 逻辑检索靠元数据和索引完成

### 4.1 推荐的目录结构

```text
docs/IPK/
  pieces/
    idea/
      2026/
    knowledge/
      2026/
    thread/
      2026/
    project/
      2026/
    review/
      2026/
    plan/
      2026/
  indexes/
  profiles/
  views/
```

更进一步，我甚至建议每个 piece 用一个单独目录，而不是单个裸文件：

```text
pieces/idea/2026/piece_20260403_001/
  piece.md
  surface.json
  links.json
```

这样做的好处是：

- 以后可以自然加入更多派生文件
- 不会把正文、摘要、索引全混在一个文件里
- 更适合后续自动化更新

## 5. Piece 不只是一层内容，而应该有多层暴露面

这是 IPK 能否真正高效工作的核心。

我建议每个 piece 至少有三层表示。

### 5.1 第 0 层：正文 `piece.md`

这是最完整的原始内容，可能包括：

- 当时的想法
- 讨论记录整理
- 问题背景
- 推导片段
- 自己的判断
- 未解决问题
- 之后的补充

这一层是“真相层”，但不能作为默认检索入口。

### 5.2 第 1 层：表层卡片 `surface.json`

这是检索和路由最重要的一层。

它应该足够短，但要足够有判断力。比如：

```json
{
  "id": "piece_20260403_001",
  "type": "idea",
  "title": "关于 anisotropic model 自对偶条件的一点直觉",
  "emoji": "💡",
  "tags": ["physics", "ising", "duality", "rg"],
  "project": ["anisotropic-ising"],
  "created_at": "2026-04-03T10:20:00+08:00",
  "updated_at": "2026-04-03T11:05:00+08:00",
  "status": "seed",
  "summary": "围绕 anisotropic square lattice 的自对偶条件形成的一条初步直觉，涉及水平和垂直耦合不同时的临界线理解。",
  "questions": [
    "这种理解是否可以自然推广到 RG 语言下？",
    "与 isotropic 情形相比，真正变化的是条件还是解释方式？"
  ],
  "claims": [
    "这一 piece 更偏直觉猜想，不是严格证明。"
  ],
  "links": ["piece_20260329_014", "piece_20260320_003"]
}
```

这层的职责不是替代正文，而是：

- 让 AI 快速判断相关性
- 让 AI 知道这个 piece 值不值得继续深挖
- 让系统快速做多维过滤和候选排序

### 5.3 第 2 层：局部展开面

未来如果 piece 很长，只靠 `surface.json` 和全文之间跳跃太大。

所以中间最好有一层轻量展开面，例如：

- `outline`
- `key_points`
- `open_questions`
- `related_concepts`
- `evidence_refs`

这一层可以单独存成 `segments.json`、`outline.md` 或嵌在 `surface.json` 的扩展字段里。

它的作用是：

- 不必整篇读取正文
- 但比一行 summary 更有判断力

## 6. Piece 的最小元数据，我建议这样设计

下面这组字段，我认为是比较稳的第一版。

### 6.1 必备字段

- `id`
- `type`
- `title`
- `created_at`
- `updated_at`
- `summary`

### 6.2 强烈建议字段

- `tags`
- `project`
- `status`
- `links`
- `emoji`

### 6.3 很有价值的结构字段

- `questions`
- `claims`
- `concepts`
- `sources`
- `confidence`
- `derived_from`

这里最重要的是：不要把标签当成唯一组织方式。

你真正需要的是几组并行的检索轴：

- 类型轴
- 项目轴
- 时间轴
- 概念轴
- 问题轴
- 关系轴
- 状态轴

## 7. 为什么关键词检索不能是主入口

你这个判断非常对。

如果只靠关键词检索，会出几个问题：

- 很多想法当时并没有用稳定术语表达
- 同一概念在不同时期可能有不同叫法
- 很多 piece 的价值不在显式关键词，而在“思路相似”“结构类似”“曾经卡在同一种问题”
- 你想要的不是“搜到含某个词的文本”，而是“找到真正对这次思考有帮助的历史片段”

所以 IPK 的检索一定不能只是：

- query string -> keyword match

而应该是：

- query intent -> route -> candidate surfaces -> expansion -> full retrieval

## 8. 推荐的检索分层

我建议把 IPK 检索分成四层。

### 8.1 第 0 层：总览索引

这层回答的问题是：

- 这个库里大概有哪些主题
- 最近在做什么
- 哪些项目最活跃
- 哪些概念反复出现
- 哪些问题长期未解

它更像全局地图，不是拿来直接回答用户问题的。

这一层的产物可以是：

- 项目总表
- 时间线总表
- 概念地图
- 活跃主题榜
- 未解决问题索引

### 8.2 第 1 层：候选路由层

这一层是最关键的低成本决策层。

当用户问一个问题时，系统先不读正文，而是根据问题选择优先从哪几个维度看：

- 项目
- 时间
- 概念
- 相关问题
- 书本或资料锚点
- 外部用户上下文

然后只拉少量候选 piece 的 `surface`。

### 8.3 第 2 层：聚焦展开层

当候选 surface 已经出现后，再对最可能相关的少数 piece 拉取：

- 局部摘要
- key points
- open questions
- 关系邻居

这一层主要用来判断：

- 是否真的值得读全文
- 是不是该沿着它的关系继续扩展
- 是该保守收缩，还是继续发散联想

### 8.4 第 3 层：正文抓取层

只有在前几层已经确认有价值时，才拉 `piece.md` 正文。

而且默认也不一定整篇读，应该优先：

- 读相关段落
- 读与当前问题关联最强的片段
- 必要时再读全文

## 9. “检索” 和 “联想” 应该分成两种 skill

你刚才问得非常准：检索的 skill 和联想的 skill 可不可以不一样？

我的答案是：**不仅可以，而且应该分开。**

原因是这两种目标天然不同。

### 9.1 检索 skill

它的目标是：

- 尽量准确
- 尽量少读
- 尽量快速锁定候选
- 尽量避免不必要的发散

它偏向：

- 收敛
- 过滤
- 判断相关性
- 路由

### 9.2 联想 skill

它的目标是：

- 跨主题连接
- 挖掘隐性相似结构
- 发现“看起来不直接相关，但可能启发当前问题”的 piece
- 帮你从旧经验、旧困惑、旧讨论里获得新启发

它偏向：

- 扩展
- 类比
- 迁移
- 弱连接探索

### 9.3 两者如何配合

最理想的顺序不是二选一，而是：

1. 先检索
2. 再联想
3. 最后整合

也就是：

- 先找最可能相关的核心材料
- 再看是否需要向外扩展一圈
- 最后生成面向用户的回答、总结或建议

## 10. 我建议的 skill 分工

如果以后要用 skill 来驱动 IPK，我建议至少拆成下面几类。

### 10.1 `ipk-capture`

负责把即时对话、微信输入、思考片段整理成新的 piece。

它做的不是“写漂亮文章”，而是：

- 识别 piece 类型
- 生成初始 summary
- 提取 tags / questions / claims / links
- 写入基础文件结构

### 10.2 `ipk-route`

负责面对一个用户问题时，先判断应该走哪条检索路径。

它回答的是：

- 先按项目找，还是先按概念找
- 先看近三个月，还是全局
- 先找历史问题，还是先找知识点

### 10.3 `ipk-retrieve`

负责严格检索。

它的要求是：

- 准
- 快
- 少读

### 10.4 `ipk-associate`

负责自由联想。

它的要求是：

- 能从关系图谱和弱连接中发现可用启发
- 但要明确标注“这是联想，不是强相关事实命中”

### 10.5 `ipk-synthesize`

负责把检索结果、联想结果、外部用户上下文和当前上下文整理成最终输出。

## 11. Piece 的关系结构必须内建

如果 IPK 想真正有“生命力”，那它不能只是卡片堆。

它必须天然支持关系。

我建议第一版至少支持这些关系：

- `related_to`
- `supports`
- `contradicts`
- `extends`
- `derived_from`
- `part_of`
- `inspired_by`
- `revisits`

这类关系比标签更重要，因为标签只能说“像不像一类”，关系才能说“它们到底怎么互相作用”。

## 12. 你真正想要的是“多维视图”，不是“多重目录”

这一点很重要。

用户看到的应该是多维视图：

- 按项目看
- 按时间看
- 按问题看
- 按概念看
- 按研究进展看
- 按最近三个月看
- 按某本书相关内容看

但底层不应该为了满足这些视图去复制存储。

所以最好的设计是：

- 存储只有一份
- 索引可以很多份
- 视图可以无限生成

## 13. 第一版最值得优先做的，不是“完美检索”，而是“正确分层”

这个功能未来会很大，但第一版最重要的不是一步到位，而是把分层做对。

第一版最应该优先保证的是：

1. `piece` 作为统一对象成立
2. 每个 piece 有稳定元数据和 surface
3. 有几条最核心的检索轴
4. 检索和联想是分开的
5. 能做到渐进披露，而不是一上来全文灌上下文

只要这五件事做对，后面无论加 embeddings、图谱、书本结构化引用、微信输入整理或外部用户适配增强，都会比较自然。

## 14. 当前推荐方案，一句话总结

当前我最推荐的方案是：

- 用 `piece` 作为统一最小单元
- 用“按类型和年份分层的目录”做物理存储
- 用 `surface` 作为 AI 默认暴露面
- 用索引来支撑项目、时间、概念、问题、状态等多维视图
- 用“检索 skill”和“联想 skill”分工协作
- 用渐进披露避免过长上下文

这套方案最能保住你最看重的核心优势：

- 不只是存
- 而是让库能真正被 AI 理解、调用、联想和发展

## 15. 下一轮最值得继续讨论的问题

下一轮我建议我们专门把两件事定下来。

### 15.1 Piece 的字段表

也就是：

- 哪些字段是必填
- 哪些字段是自动提取
- 哪些字段由 AI 维护
- 哪些字段由用户显式确认

### 15.2 索引层最小集合

也就是第一版到底先做哪几份索引最划算，例如：

- `by_project`
- `by_time`
- `by_type`
- `by_concept`
- `open_questions`
- `piece_links`

这两件事一旦定下来，IPK 的底座就会非常清楚。
