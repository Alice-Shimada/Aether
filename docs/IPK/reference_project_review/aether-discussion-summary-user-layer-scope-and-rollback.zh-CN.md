# Aether 用户层、作用域冲突与条目化习惯库讨论纪要

> 状态：已完成  
> 日期：`2026-04-18`  
> 目的：把本轮围绕 Aether 用户自适应系统的延伸讨论沉淀成一份可复用纪要，供后续外部项目复审、Aether 设计讨论、以及实现前再核对时直接引用。  
> 方法说明：本纪要基于 `docs/IPK/reference_project_review` 全目录扫读和重点精读形成，重点参考了 `round-1-overview`、`cross-project-synthesis`、专题复审目录、以及 `mem0 / graphify / graphiti / Hermes / OpenClaw / Letta / Zep / LangGraph` 等代表项目。

## 0. 一句话结论

Aether 现在最有潜力的路线，不是简单照搬某个外部项目，而是把下面三件事组合起来：

- 用分层 `.md` 视图保存稳定、可读、可审计的运行时入口；
- 用条目化、带作用域、结构化的习惯库保存长期真源；
- 用运行时编译层决定当前 session 里到底激活哪些规则。

换句话说，Aether 最值得继续深化的不是“统一大记忆池”，而是：

> 条目真源 + 分层视图 + 运行时编译 + 作用域治理 + 可回滚。

## 1. 这轮讨论真正聚焦的几个问题

本轮讨论不是在重问“要不要做用户自适应”，而是在继续收敛下面几个更难的问题：

- 一个 session 内，习惯库抓取的时机到底应怎样设计。
- 是否需要一层稳定用户层，例如 `USER.md`。
- `USER.md` 和当前 session 显式要求冲突时，谁优先。
- 多作用域条目能否显著降低冲突。
- 条目化习惯库是否比纯 `.md` 方案更适合治理、回滚和结构化检索。
- 外部项目里是否已经有人把“已存记忆回滚”和“作用域边界”做得足够成熟。

## 2. 关于当前 session 中反复抓取习惯的判断

### 2.1 当前机制不是错的

Aether 现在这套机制可以概括为：

- 用户在当前 session 里提出新要求；
- 系统更新 `session scratch`；
- 同时重新从长期习惯库抓取相关习惯；
- 再形成当前 active set。

这件事本身是有价值的，因为它解决的是一个真实问题：

- 用户的要求会在一个长 session 内继续演化；
- 模型未必会稳定记住前面所有细节；
- 如果不刷新，系统容易继续沿用旧规则。

所以，把它视为“session 内活跃层刷新机制”，这是合理的。

### 2.2 但它不适合继续承担稳定用户层主入口

外部成熟项目里更常见的主模式是：

- 先有一层很小、很稳、默认常驻的稳定用户层；
- 再有 session 内变化层；
- 再有更宽的 recall / graph / history / archive 层。

因此，Aether 当前机制最准确的定位不是“稳定用户注入主机制”，而是：

> session 内的动态活跃层刷新机制。

如果继续让“每轮重新从长期习惯库抓取”承担主要稳定用户入口，会带来几类问题：

- 运行时默认行为容易抖动；
- 稳定用户认知和临时要求更容易混写；
- prompt 装配不够稳定；
- 解释起来更困难；
- 后续接入 `session recall` 或更宽记忆层时边界会越来越乱。

### 2.3 最合适的收束方式

本轮讨论后的更稳判断是：

- 保留现在这套 session 内刷新机制；
- 但把它降级为“活跃层刷新”，而不是“稳定层入口”；
- 另补一层小而稳定、默认常驻的用户层。

可以压成一句话：

> 稳定层少变，活跃层常变。

## 3. `USER.md` 到底像不像现在的 `global`

### 3.1 像，但不等于

本轮讨论形成的判断是：

- `global` 更像作用域概念；
- `USER.md` 更像运行时稳定用户视图。

也就是说：

- `global` 回答的是“这条规律适用于多大范围”；
- `USER.md` 回答的是“这一轮默认该带上哪几条最重要的稳定用户信息”。

### 3.2 更准确的关系

最稳的理解方式是：

- `confirmed habits`：长期真源；
- `global`：长期真源里跨任务成立的那部分作用域；
- `USER.md`：从长期真源中挑出最稳定、最值得默认常驻的少量信息，形成稳定用户层；
- `session scratch`：当前 session 临时变化层。

所以更精确的说法不是：

- `USER.md = global`

而是：

- `USER.md` 更像“以 `global` 为主、由 confirmed habits 编译出来的一张稳定用户卡片”。

### 3.3 一个重要约束

如果以后真的引入 `USER.md`，最稳的设计不是把它做成另一个独立真源，而是优先把它做成：

> 条目真源的编译视图。

否则很容易出现双真源漂移：

- 条目库改了，但 `USER.md` 没改；
- `USER.md` 被人手改了，但真源没同步；
- 运行时不知道该信哪一层。

## 4. 冲突优先级：为什么这是最难的问题

### 4.1 关键冲突不在“有没有记忆”，而在“谁覆盖谁”

真正棘手的不是是否有：

- 习惯库；
- `USER.md`；
- `session scratch`；
- recall / graph / history。

而是它们一旦冲突，系统到底怎么处理。

典型问题就是：

- `USER.md` 说“平时回答详细一点”；
- 当前 session 用户又说“这次请你非常简短”。

如果系统继续听 `USER.md`，用户会觉得它不听话。  
如果系统让本次要求直接永久覆盖 `USER.md`，长期层又会被偶发情况污染。

### 4.2 这轮讨论形成的最小优先级

本轮形成的最小优先级表是：

1. 当前 session 的显式要求  
2. 稳定用户层，例如 `USER.md`  
3. confirmed habits 真源  
4. session recall / 通用记忆层  
5. assistant 侧自动推断结果

这个顺序表达的不是“越下面越没用”，而是：

- 越上面越直接决定当前这轮行为；
- 越下面越像证据、背景或候选。

### 4.3 一个关键治理原则

当当前 session 显式要求和稳定用户层冲突时，更稳的处理应该是：

- 当前 session 显式要求优先；
- 但只在本 session 生效；
- 不自动改写稳定用户层；
- 最多把它作为后续 proposal / signal。

这条原则非常重要，因为它同时保护了：

- 当前可用性；
- 长期层稳定性；
- 回滚能力；
- 用户解释边界。

## 5. 外部项目有没有把这个问题真正解决

### 5.1 结论：大多只解决了“怎么减冲突”，没有完整解决“最终优先级”

本轮比对后形成的判断是：

- 外部项目普遍知道要分层；
- 但很少公开给出一张足够清楚、足够成熟的最终冲突优先级表。

它们更常见的做法是：

- 把稳定层和动态层拆开；
- 把用户层和一般记忆层拆开；
- 把 session recall 和 profile 拆开；
- 靠分层减少冲突，而不是把所有冲突都用一张规则表硬解。

### 5.2 代表项目的启发

- `Hermes`
  它把 `USER.md`、`MEMORY.md`、`session_search`、provider profile 等层分得很清楚，但公开材料并没有完全讲清楚这些层同时出现时的最终优先级。
- `Zep`
  它有 `user summary + graph` 的组合，但 summary 和 graph 冲突时谁最终覆盖谁，公开说明仍不充分。
- `Letta`
  它有很强的常驻 core block，例如 `human / persona`，但 core、summary、archival 叠加后的冲突治理也并没有被完全公开讲清楚。
- `OpenClaw`
  它更像通过 workspace bootstrap files、session memory、active memory、Honcho 等多层拆分，尽量避免把冲突正面压成一个统一优先级问题。

因此，本轮可以得出的更真实结论是：

> 外部项目给了很多“分层减冲突”的启发，但没有谁给出一套已经成熟到可以直接照搬的公开标准答案。

## 6. 为什么条目化 + 作用域 + 结构化习惯库很有潜力

### 6.1 这条路线的核心优势

你现在这条思路之所以强，不是因为它只是“更好管理”，而是因为它天然让几个原本模糊的问题变成了可治理问题：

- 冲突的是哪一条；
- 冲突发生在哪个作用域；
- 应该改长期真源、运行时视图，还是 session 临时层；
- 需要回滚哪一条，而不是整份文档。

这比很多只靠整份 `.md` 管理的项目更细，也更适合真正做冲突治理。

### 6.2 它特别适合做回滚

条目化 + scope 的价值还体现在回滚上：

- 可以做单条回滚；
- 可以做某个作用域下的局部回滚；
- 可以做版本回滚；
- 可以做失效化，而不是物理删除；
- 可以只撤销本 session 的 active override，而不改长期真源。

如果后续再补上：

- 版本历史；
- 来源链路；
- 写入时间；
- 用户确认记录；

那这套体系在“可审计、可回滚”上会比多数外部项目更强。

### 6.3 但这条路线也有自己的难点

需要提前承认几个风险：

- 作用域判错会比“不设作用域”更隐蔽；
- 同义或近重复条目可能分布在多个作用域；
- 运行时 active set 编译会变复杂；
- 用户解释界面也要跟上，否则内部很清楚、外部却难懂；
- 以后跨 workspace / cross-project 共享时，边界需要更精细。

所以这条路线不是没有难点，而是：

> 它把问题变得更复杂，但也变得更可治理。

## 7. 外部项目里有没有“作用域区别”

### 7.1 有，但大多更粗

外部项目里很多都已经知道“要分边界”，只是它们通常把边界放在：

- 用户 / agent / org / run；
- thread / checkpoint / store；
- workspace / bootstrap files；
- graph 分组；
- 独立文件层。

它们多数不是像 Aether 这样，直接把 rich scope 下沉到每条习惯条目本身。

### 7.2 本轮比较中比较有代表性的几类

- `mem0`
  有 `user_id / run_id / agent_id / org` 这类 scope，说明它很重视作用域，但它更偏存储边界，不是 Aether 这种语义作用域。
- `OpenClaw`
  很强调 workspace 和 session routing，很像“某些信息只作用于某个工作区或某类会话”。
- `Hermes`
  主要靠 `USER.md / MEMORY.md / SOUL.md / session_search / skills` 这些不同文件和层来表达边界。
- `LangGraph`
  强调 `thread / checkpoint / store / runtime context`，是状态层和存储层的边界。
- `Graphiti`
  通过 `group_id` 分区，很像租户级或工作区级边界。

### 7.3 对 Aether 的真正启发

外部项目已经证明：

- 没有边界不行；
- 有分层很重要；
- 但边界大多还比较粗。

Aether 当前的潜在优势在于：

> 不只是“有边界”，而是“把边界落到每条习惯记录本身”。

这比一般的“文件分层”更难，但也更适合解决你最关心的冲突和回滚问题。

## 8. 外部项目里有没有对已存记忆做回滚

### 8.1 结论：有接近回滚的能力，但少有成熟公开的细粒度回滚系统

本轮讨论后的判断是：

- 有些项目能做审计、删除、重置、保留历史；
- 有些项目能做时间化事实失效；
- 也有项目开始走版本化路线；
- 但真正成熟、公开、细粒度的“把某条长期记忆回到某个旧版本”的系统很少。

### 8.2 几类值得参考的路线

- `Letta`
  最接近“版本化回滚”。它的 `git-backed memory` 很值得关注，但公开材料里对“用户画像如何回滚”仍不够完整。
- `mem0`
  更像“审计 + 删除 + reset + history”，适合追踪和清理，但不完全等于细粒度版本回退。
- `Graphiti`
  它擅长的是“保留历史并标记失效”，不是传统意义的回滚；但这对偏好变化和事实变更很有启发。

### 8.3 Aether 的机会

如果 Aether 把下面这些结合起来：

- 条目化；
- 作用域；
- 版本；
- 来源；
- 失效状态；
- 运行时 active override；

那在“可回滚的用户自适应真源”这件事上，反而有机会比外部公开案例走得更清楚。

## 9. `.md` 分层和条目真源为什么最好组合起来

### 9.1 只用 `.md` 的长处和短板

只用 `.md` 分层的长处是：

- 人好读；
- 稳定；
- 审计方便；
- 适合做默认运行时入口。

短板是：

- 细粒度更新困难；
- 冲突治理粗；
- 局部回滚不自然；
- 容易退化为整份文件管理。

### 9.2 只用条目池的长处和短板

只用条目化 memory substrate 的长处是：

- 结构化；
- 好检索；
- 好局部更新；
- 好做 scope；
- 好做回滚。

短板是：

- 人不容易一眼看懂“当前系统怎样理解我”；
- 稳定默认入口可能不够清晰；
- 运行时如果没有中间视图层，容易发散。

### 9.3 最强组合方式

本轮讨论后的最强组合不是二选一，而是：

- 条目化习惯库做真源；
- `USER.md` / `global_guidance` / 其他 `.md` 做分层视图；
- 运行时再用 context compiler / active set 去编译当前 session 真正需要的部分。

可以压成一句话：

> `.md` 负责“给人看得懂”，条目库负责“给系统管得住”。

### 9.4 一个必须守住的约束

这套组合要成立，必须只有一个真源。

更推荐的路线是：

- 条目化习惯库是真源；
- `.md` 层是编译视图或稳定入口；
- `.md` 不应成为另一套可独立漂移的长期真源。

如果两边都能独立写、独立演化，系统很快就会出现：

- 双真源漂移；
- 解释冲突；
- 回滚困难；
- 用户不知道该改哪一层。

## 10. 这份纪要可直接反问外部项目的审查清单

以后再审一个外部项目时，可以直接用下面这些问题反问它：

- 它有没有稳定用户层，还是完全靠每轮动态召回。
- 它的稳定用户层和当前 session 显式要求冲突时，谁优先。
- 它把用户层、session recall、一般记忆层、程序性技能层分开了吗。
- 它的用户适配真源是整份文档，还是条目化结构。
- 它能不能只更新某一条长期偏好，而不是整体重写 profile。
- 它有没有 scope 或等价边界，边界落在文件、用户、线程、工作区，还是落在单条记录。
- 它的回滚是删除、reset、保留历史失效，还是能回到旧版本。
- 它的运行时视图和长期真源是不是同一层。
- 它是不是有双真源问题。
- 它能不能解释“为什么这一轮用了这条规则”。

## 11. 当前对 Aether 的收束判断

把这轮讨论最终收束到 Aether 本身，可以得到下面几条稳定判断：

- 当前 session 内反复抓取机制是有价值的，应保留，但它更适合作为活跃层刷新机制。
- Aether 需要一层小而稳定、默认常驻的稳定用户层。
- 这层稳定用户层更适合做成条目真源的编译视图，而不是独立真源。
- `USER.md` 和当前 session 显式要求冲突时，应该由当前 session 要求优先，但只影响本 session。
- 条目化 + scope + 内部结构化管理，是 Aether 解决冲突和支持回滚的很强路线。
- 外部项目普遍证明了“边界必须存在”，但很少把边界做到 Aether 现在想做的每条习惯级别。
- `.md` 分层和条目化真源不是替代关系，而是最值得组合起来的两种能力。

## 12. 最后一句话

如果把这轮讨论压成一句可以长期反复引用的话，那就是：

> Aether 不应该在“稳定入口”和“细粒度治理”之间二选一，而应该把稳定用户视图、条目化习惯真源、作用域治理、运行时编译和回滚能力组合成一套系统。
