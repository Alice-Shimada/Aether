# 用户自适应系统双线推进路线

状态：讨论收敛稿，供后续产品和架构推进参考，不替代最高约束、实现决策或 v1 实施指南。  
日期：2026-04-18

## 0. 目的

这份文档把当前关于“短期先做什么、长期真正想做什么”的建议收成一份可执行路线。

它主要回答四个问题：

- 为什么当前适合双线推进，而不是只押一条路线。
- 短期为什么适合以 Hermes 为基础做第一版应用。
- 长期为什么仍然应继续保留 Aether 当前这套更强结构，作为后续新系统。
- 两条线之间怎样分工、怎样迁移、怎样避免互相拖累。

这份文档是路线文档，不是权威约束文档。

- 最高结构约束仍以 [user-adaptation-system-top-level-constraint.zh-CN.md](/home/bzz/Aether/docs/IPK/02-user-adaptation-system/user-adaptation-system-top-level-constraint.zh-CN.md) 为准。
- 已拍板实现边界仍以 [user-adaptation-system-implementation-decisions.zh-CN.md](/home/bzz/Aether/docs/IPK/02-user-adaptation-system/user-adaptation-system-implementation-decisions.zh-CN.md) 为准。

## 1. 一句话结论

当前最稳的方向不是“只走 Hermes”或“只走 Aether 当前结构”，而是：

- 短期线：用 `Hermes 风格的产品骨架 + Aether 风格的治理边界`，尽快做出一个真实可用的第一版应用。
- 长期线：继续发展 `Aether 的条目真源 + 多作用域 + review + runtime 编译` 路线，把它作为后续新系统，而不是被第一版应用的时间压力拖着简化。

## 2. 为什么适合双线推进

### 2.1 当前真实矛盾

当前最核心的矛盾不是“哪个系统更先进”，而是：

- Hermes 路线更接近成熟产品骨架，更容易快速做出“明显更懂用户”的体验。
- Aether 当前路线更适合长期做成一个强治理、强结构、强可回滚的系统，但短期工程成本更高。

如果只走 Hermes 路线，主要风险是：

- 很快能做出产品，但长期容易积累边界污染。
- 用户层、任务经验层、历史会话层容易慢慢混写。
- 后面想补治理、回滚、作用域时，改造成本会越来越大。

如果只走 Aether 当前路线，主要风险是：

- 会花很多时间在作用域、审查、存储、图谱、解释边界上。
- 第一版应用不一定很快形成清晰、稳定、明显的用户价值。
- 容易先做出“设计上很完整”的系统，但不够快地获得真实产品反馈。

### 2.2 双线推进各自解决什么

- 短期线解决“尽快做出一个可用应用”。
- 长期线解决“以后怎样做出一个根本上更强、更有优势的新系统”。

因此双线推进不是重复建设，而是把两个不同目标分开承载：

- 产品落地目标由短期线承担。
- 架构创新目标由长期线承担。

## 3. 短期线定位

### 3.1 短期线的产品目标

短期线要解决的，不是“把用户自适应理论一次做完整”，而是：

- 让系统从第一轮开始就更像“认识这个用户”。
- 让稳定用户偏好能持续影响回答，而不是每次重猜。
- 让用户可以逐步修正系统对自己的理解。
- 让第一版应用尽快积累真实交互反馈。

### 3.2 为什么 Hermes 适合作为短期基础

Hermes 最值得借的不是“有 memory”，而是它把一个长期 agent 产品最关键的几层分清了：

- 稳定用户层，例如 `USER.md`
- 更宽的一般记忆层，例如 `MEMORY.md`
- 独立的历史会话回忆层，例如 `session search`
- turn 前读取、turn 后同步的清晰生命周期

这套结构对第一版应用特别重要，因为它直接回答了一个产品问题：

> 每轮开始时，系统怎样先带着一小块稳定用户信息工作，而不是每次都临时判断？

## 4. 短期线建议保留的 Hermes 核心

### 4.1 保留一层稳定用户层

短期线必须有一层“小而稳定、默认带上”的用户层。

这层适合放：

- 用户沟通偏好
- 用户稳定工作方式
- 用户已知背景
- 用户长期不喜欢的回答或执行方式
- 少量高价值长期事实

主要优点：

- 每轮都稳定。
- prompt 编排很直接。
- 用户很容易感受到“系统认识我”。

主要缺点：

- 一旦写错，会每轮都错。
- 如果内容失控变大，会变成稳定污染源。

建议实现手段：

- 先做成一个小型结构化摘要或小文本块。
- 严格限制长度，只保留高价值稳定信息。
- 初期默认只读，不允许 agent 直接改正式内容。

### 4.2 保留“用户层”和“一般记忆层”分离

短期线应明确分开：

- 用户是谁
- 系统知道了哪些任务、环境、项目、工具经验

这样做的主要优点：

- 冲突更少。
- 用户更容易理解。
- 后面向 Aether 长期线迁移更容易。

主要缺点：

- 初期必须先定边界。
- 某些信息在归类时会有模糊区。

建议实现手段：

- `USER` 层只放用户稳定信息。
- `MEMORY` 层放项目、环境、任务经验。
- 第一版不继续新增太多层，先保持简单。

### 4.3 保留独立的 session recall

短期线不要把历史会话直接当成用户画像。

应该单独保留一层：

- 会话回忆

而不是把它直接塞进：

- 稳定用户层
- 一般记忆层

主要优点：

- 不容易把一次聊天误当长期习惯。
- 能支持“我们上次聊到哪里”的真实需求。
- 产品行为更接近成熟长期助手。

主要缺点：

- 多一层检索与装配逻辑。
- 如果没有边界控制，容易让 prompt 逻辑变复杂。

建议实现手段：

- 先做轻量 session recall。
- 默认按需调用，不做大规模常驻注入。
- 只在“继续任务”“用户提到上次内容”“当前消息明显依赖历史”时触发。

### 4.4 保留 turn 前 prefetch、turn 后 sync 的节奏

短期线很适合用下面这个节奏：

- turn 前：加载稳定用户层和少量 recall。
- turn 后：从当前消息中提取候选，但不直接改长期层。

主要优点：

- 生命周期清楚。
- 容易调试。
- 用户感受稳定，不容易出现“这轮突然人格漂移”。

主要缺点：

- 如果 turn 后写入策略过强，还是会污染长期层。

建议实现手段：

- turn 前只读少量高价值信息。
- turn 后只生成候选，统一进入 review/inbox。

### 4.5 保留显式、可编辑真源

短期线依然应保留用户相关信息的显式真源。

这件事非常重要，因为它保证：

- 可审计
- 可解释
- 可手工修正

主要优点：

- 不会完全黑箱化。
- 便于快速定位错误。
- 便于观察第一版到底积累了哪些真实高价值信息。

主要缺点：

- 要设计最小编辑入口。
- 需要防止真源变成无结构信息堆积区。

建议实现手段：

- 初期允许文件式或简单表格式真源。
- 即使前端不完整，也要保证开发阶段可直接查看和修正。

## 5. 短期线建议删减的 Hermes 能力

### 5.1 不要让 agent 直接改稳定用户层

这是短期线最应该主动删掉的一点。

删除原因：

- 当前产品心智更重视用户确认和可治理。
- 直接自动写入稳定用户层，误写成本过高。

替代方案：

- agent 只提候选
- 用户确认后才写稳定用户层

### 5.2 不要过早引入强自动 provider 用户建模

删除原因：

- 自动能力强，但黑箱感也强。
- 现在还没有把层边界和治理机制打稳。
- 会干扰第一版对真实价值点的观察。

替代方案：

- 第一版只做轻量提取和 review。
- 外部动态建模延后到更宽记忆层或长期线实验阶段。

### 5.3 不要过早深度耦合 skill layer

删除原因：

- “用户是谁”和“这类任务怎样做”现在仍应先分开看。
- 一开始把 skill layer 做深，容易把长期用户层和程序性经验层混写。

替代方案：

- 只保留少量 workflow preference。
- 暂不做完整 skill system。

### 5.4 不要做过宽的自动长期化

删除原因：

- 第一版最容易失败的地方，就是把太多临时内容升格为长期事实。

替代方案：

- 稳定用户层很小。
- 一般记忆层可以略宽。
- 会话层最宽，但默认短命。

## 6. 短期线建议主动增加的能力

这一节讨论的不是“删什么”，而是：

> 如果短期线只是删减版 Hermes，它仍然不够像 Aether 想做的方向。  
> 所以第一版还应该主动补几样小而关键的能力。

### 6.1 加一个明确的 review gate，而不是直接写长期层

来源：

- `Aether` 的 proposal / review
- `memos` 的显式可控
- `openclaw` / `hermes` 的可编辑真源

更稳的第一版应是：

- turn 后可以自动提取候选
- 候选先进入 review queue / inbox
- 用户确认后才写入稳定用户层

建议实现手段：

- 先做轻量 review gate
- 候选卡片展示摘要、来源消息、建议归类
- 默认只做 `确认 / 忽略 / 稍后处理`

### 6.2 加一个“当前生效集合”视图

来源：

- `Aether` 的 active set
- `letta` / `zep` 对运行时生效信息的重视

短期线里，用户不只需要知道系统“存了什么”，还需要知道“这一轮什么真的在生效”。

建议实现手段：

- 第一版只做一个小面板或弹窗
- 按来源分成 `稳定用户层`、`会话回忆`、`一般记忆`
- 每条只展示短摘要和来源

### 6.3 加一个轻量 scope 机制，但不要把五层 scope 全搬进第一版

来源：

- `Aether` 的多作用域
- `mem0` 的朴素 scope
- `langgraph` 的 thread / store / runtime context 分层

短期线虽然不适合一上来就完整前台化五层 scope，但也不应完全没有作用域概念。

更稳的做法是先保留一个轻量版本，例如：

- `只这次`
- `当前任务`
- `长期用户`

建议实现手段：

- 用户前台先只看自然语言范围
- 后台保留可迁移字段
- 所有“作用域扩大”默认进 review

### 6.4 加上时间性和反证，而不是只做静态长期记忆

来源：

- `graphiti` 的时间事实
- `zep` 的用户状态变化
- 推荐系统对“长期偏好 / 短期状态”的区分

第一版至少要保留：

- 每条稳定信息的更新时间
- 用户明确改口时，旧信息可失效或降权

建议实现手段：

- 不做完整时间图谱
- 至少保留 `last_confirmed_at`、`last_seen_at`、`superseded_by`
- 用户明确改口时，优先替换而不是简单追加

### 6.5 加一个有界主动召回，而不只是被动检索

来源：

- `openclaw` 的 active memory
- `zep` 的 user context
- `hermes` 的 prefetch

如果只有“消息来了再临时搜”，仍然容易错过本该被带上的少量关键信息。

建议实现手段：

- 只做 bounded preflight recall
- 严格限制 top K、超时和来源范围
- 优先从当前任务、最近 session、稳定用户层相关项中取回少量片段

### 6.6 加一个“真源 / 派生视图 / 检索索引”分离意识

来源：

- `openclaw`、`graphify`、`graphiti` 的真源/派生层区分
- `Aether` 对长期真源和运行时层分开的坚持

即使第一版不做复杂图谱，也不应把“用户真源、展示视图、检索索引”混在一起。

建议实现手段：

- 明确哪个对象是正式真源
- 稳定用户卡片视为渲染视图，不是唯一真源
- recall 用缓存、embedding、summary 都视为派生层

### 6.7 这一节的总判断

因此，短期线不应只是“做一个删减版 Hermes”，而更适合做成：

> `Hermes 的产品骨架 + Aether 的 review / active set / 轻量 scope / 真源边界`

如果把这一节压成最小行动项，第一版最值得额外加入的是：

1. review gate
2. 当前生效集合视图
3. 三档轻量 scope
4. 最小时间性与反证
5. bounded 主动召回

## 7. 短期线推荐结构

### 7.1 推荐最小结构

第一版应用建议只保留三类核心对象：

1. 稳定用户层
2. 会话回忆层
3. 一般记忆层

### 7.2 推荐数据流

```text
当前消息
  -> turn 前
     读取稳定用户层
     读取少量会话回忆
     读取少量一般记忆
  -> 生成回答
  -> turn 后
     提取候选
     分流为：
       用户稳定候选
       会话回忆候选
       一般记忆候选
  -> 进入 review / inbox
  -> 用户确认后再写稳定用户层
```

### 7.3 这条线的本质

短期线本质上是：

> `Hermes 的产品骨架 + Aether 的治理边界`

也就是：

- 用 Hermes 的结构让系统尽快好用。
- 用 Aether 的审查边界避免第一版把长期层写坏。

## 8. 短期线的优点、缺点与适用目标

### 8.1 主要优点

- 很快能做出“明显更懂用户”的体验。
- 产品形态直观，容易验证用户是否真的在乎这些能力。
- 更容易获得真实使用反馈，而不是只积累设计判断。
- 以后可以作为长期线的实验基线和对照组。

### 8.2 主要缺点

- 作用域粒度较粗。
- 长期治理能力有限。
- 冲突和回滚能力不如 Aether 长期线自然。
- 容易逐渐演变成“经验型记忆产品”，而不是结构化用户自适应系统。

### 8.3 适用目标

短期线更适合承载：

- 第一版应用
- 快速验证用户价值
- 早期产品演示
- 收集真实交互样本

它不适合作为最终长期架构。

## 9. 长期线定位

### 9.1 长期线的目标

长期线不是要继续堆更多功能，而是要做一个根本上更强的系统。

这个系统最终应更擅长：

- 不乱记
- 不乱用
- 不乱放大
- 不乱污染
- 出错后能清楚地改回来

### 9.2 长期线为什么仍应坚持 Aether 当前路线

当前 Aether 路线真正强的地方，不是层级更多，而是它在回答更难的问题：

- 一条规则到底适用于多大范围
- 当前 session 明确要求和长期规则冲突时怎么办
- 长期真源、工作区引用、当前活跃集怎样分开
- 哪些内容只是候选，哪些是正式真源
- 出错后如何局部回滚，而不是整块重写

这些问题一旦进入长期使用阶段，会比“能不能记住用户”更重要。

## 10. 长期线最值得继续保留的骨架

### 10.1 三块架构

长期线应继续保留：

- 独立习惯库真源
- Aether 工作区引用层
- session scratch

这套结构天然防止：

- 长期真源和运行时状态混在一起
- 临时要求和长期规则混在一起
- 用户信息和更宽记忆层混在一起

### 10.2 多作用域

长期线应继续保留：

- `global`
- `subject`
- `initiative`
- `task_scope`
- `artifact`

它们的价值不在“更复杂”，而在于允许系统表达：

- 不是所有长期信息都全局适用
- 不是所有习惯都该每轮自动带上
- 长期有效不等于所有场景生效

### 10.3 scratch 机制

长期线应继续保留 `scratch`，因为它稳定回答了一个关键问题：

- 当前先听话
- 长期以后再决定

这层不能丢。

### 10.4 proposal / review

长期线应继续保留 proposal / review，因为它是系统可治理性的核心。

没有这层，长期系统很容易滑向：

- 自动写入越来越多
- 用户越来越难纠错
- 运行时越来越难解释

### 10.5 条目真源 + 派生视图

长期线最有潜力形成优势的地方，是下面这个组合：

- 真源是结构化条目
- 用户看到的是稳定视图
- 运行时用的是编译结果
- explain / graph / report 都只是派生层

这条路线长期可扩展性很强。

## 11. 长期线当前最该补的部分

### 11.1 不是继续加更多 scope

长期线当前最缺的，不是再新增层，而是：

- 一层小而稳定、默认总带上的用户层

### 11.2 建议新增“稳定用户视图”

这层更适合理解成：

- compiled stable user view

而不是：

- 新的独立真源

推荐关系是：

- confirmed habits 是长期真源
- `global` 等 scope 仍表示适用范围
- 稳定用户视图是从 confirmed habits 编译出来的运行时稳定入口
- `session scratch` 则继续承担当前 session 的变化层

也就是说：

> 长期线不应做第二真源，而应做“由条目真源编译出来的稳定用户视图”。

### 11.3 这样做的主要优点

- 不会造成双真源漂移。
- 运行时默认入口更稳定。
- 更容易和短期线的 `USER` 层形成迁移关系。

### 11.4 这样做的主要风险

- 编译逻辑本身会变成新的关键系统。
- 需要认真定义“哪些条目值得进入稳定用户视图”。
- 需要认真定义和 `scratch`、confirmed habits、future memory layers 的优先级。

## 12. 长期线后面真正能形成的优势

长期线以后真正能超过 Hermes 风格系统的，不是“记得更多”，而是下面这些能力：

- 作用域正确性
- 冲突治理
- 局部回滚
- 来源可追溯
- 时间有效性
- 运行时 active set 可解释

这几项能力组合起来，才是 Aether 长期线真正可能形成根本优势的地方。

## 13. 两条线怎样分工，避免互相拖累

### 13.1 短期线负责什么

短期线负责回答：

- 怎样快速做出一个好用的第一版应用
- 怎样让系统明显更懂用户
- 用户最在乎哪些长期信息
- 稳定用户层最小该长什么样

### 13.2 长期线负责什么

长期线负责回答：

- 真源怎样建模
- scope 怎样治理
- scratch / proposal / promotion / rollback 怎样成立
- 编译视图和运行时 active set 怎样表达
- session recall / 通用记忆 / 程序性技能层以后怎样接入

### 13.3 一条重要边界

- 不要让 Hermes 短期线承担最终理论正确性。
- 不要让 Aether 长期线承担第一版必须尽快上线的时间压力。

## 14. 两条线之间的迁移关系

### 14.1 推荐迁移方向

未来更稳的迁移方向应是：

- 短期线的 `USER` 层，逐步迁移为长期线里的“稳定用户视图”。
- 短期线的一般记忆层，未来拆分到 session recall、任务记忆或更宽通用记忆层。
- 短期线里保守的 review 机制，迁移为长期线里的 proposal / promotion / rollback 治理流程。

### 14.2 不推荐的迁移方向

不建议以后直接把短期线积累的所有 memory 原样灌进长期条目真源。

原因：

- 其中会混有不同生命周期的信息。
- 其中会混有用户层、任务层、环境层、会话层。
- 如果不先重分类，会直接污染长期线真源。

## 15. 当前建议的实际推进方式

### 15.1 短期线建议

当前更适合推进：

- Hermes 风格产品骨架
- 稳定用户层
- 一般记忆层
- session recall
- turn 前 prefetch / turn 后 candidate sync
- review gate

当前不建议优先推进：

- 强自动 provider 用户建模
- 完整 skill layer
- 重型图谱
- 完整五层 scope 的用户前台化

### 15.2 长期线建议

当前更适合推进：

- 保留三块架构
- 继续保留 confirmed habits / scratch / proposal
- 补出 compiled stable user view
- 继续完善 scope / runtime active set / explain / rollback 边界

当前不建议为了短期产品压力而被迫推进：

- 把长期线退化成单层 memory 池
- 取消 proposal / review
- 让工作区层复制长期真源

## 16. 当前阶段的推荐判断

如果把当前判断压成一句最短建议，就是：

> 短期先做“`Hermes 的产品骨架 + Aether 的治理边界`”，长期再做“`Aether 的结构骨架 + 稳定用户视图 + 更宽记忆层编排`”。

如果把它再展开成两个更直接的动作：

1. 第一版应用：先做一个删减后的 Hermes 改造版。
2. 后续新系统：继续以当前 Aether 路线为主干，但先补稳定用户视图，再接 session recall / 通用记忆 / 程序性技能层。
