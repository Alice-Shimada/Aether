## 0. 先给结论

这个项目是否有明确用户自适应系统：

> `几乎没有，这不是它的重点`

一句话说明：

> `memos` 更像“让用户自己掌管知识资产”的工具，而不是“系统自动学会用户习惯”的工具；它只有少量显式用户设置，不做自动用户画像。

## 1. 项目自己的用户需求判断

这个项目似乎认为用户真正需要：

- 快速记录，不被复杂结构打断。
- 数据属于自己，可迁移、可自托管、可控。
- 通过显式设置控制界面与默认行为，而不是让系统猜。

这些判断来自：

| 证据类型 | 位置 | 说明 |
| --- | --- | --- |
| 文档证据 | `README.md` | 重点写的是 quick capture、data ownership、markdown-native。 |
| 代码证据 | `proto/store/user_setting.proto` | 用户设置只有 locale、memo_visibility、theme 等显式项。 |
| 代码证据 | `server/router/api/v1/user_service.go` | 只能更新自己的 settings，且字段非常有限。 |
| 推断 | 基于产品整体结构 | 它显然不认为“自动推断用户习惯”是核心功能。 |

## 2. 它把用户自适应叫什么

| 项目术语 | 含义 | 是否等同 Aether 的用户画像 / 习惯 |
| --- | --- | --- |
| general user setting | 用户显式保存的界面和默认行为设置 | 只是一小部分显式偏好 |
| theme | 界面主题 | 不是 agent 用户画像 |
| locale | 语言区域偏好 | 部分相似，但很浅 |
| memo_visibility | 默认可见性 | 是内容策略，不是人物画像 |

## 3. 用户信息从哪里来

| 来源 | 是否用户显式提供 | 是否模型自动提取 | 是否有证据保存 | 风险 |
| --- | --- | --- | --- | --- |
| 用户设置表单 | 是 | 否 | 是 | 风险低，可审计 |
| 当前登录用户身份 | 是 | 否 | 是 | 主要用于权限，不是适配 |
| memo 内容 | 是 | 否 | 是 | 这是用户内容，不是系统自动画像 |
| AI provider 配置 | 管理员显式配置 | 否 | 是 | 影响辅助能力，不等于用户适配 |

## 4. 用户信息怎样影响行为

```text
用户修改自己的 general settings ->
API 校验当前用户身份 ->
UpsertUserSetting ->
前端按 theme / locale / memo_visibility 展示和默认行为调整
```

说明：

- `memos` 读取用户信息的主要时机是渲染和默认值设置。
- 用户信息并不进入 agent prompt 组装主链路。
- 最终改变的是界面主题、语言和 memo 默认可见性，而不是回答策略。

## 5. 写入、更新、纠正和删除

| 动作 | 触发条件 | 用户是否确认 | 关键代码 / 文档 | 评价 |
| --- | --- | --- | --- | --- |
| 写入 | 用户显式保存设置 | 是 | `user_service.go`、`user_setting.proto` | 很克制，几乎无误判空间 |
| 更新 | 用户再次修改设置 | 是 | `user_service.go` | 显式覆盖，简单可靠 |
| 纠正 | 继续修改设置 | 是 | `user_service.go` | 不需要额外治理机制 |
| 删除 | 首轮未见单独删除 general settings API | 是，由后续覆盖替代 | `user_setting.go` | 它把设置当普通配置，不强调复杂生命周期 |

## 6. 作用域和边界

它是否区分：

- 全局用户偏好：有，但只限显式 general settings
- 项目级偏好：没有明显 agent/project 级 profile
- 会话内临时偏好：没有作为独立系统出现
- 外部知识内容：memo 本身是内容资产，不是 profile
- agent 自己的经验：没有

结论：

> `memos` 的边界非常清楚：用户设置是设置，memo 内容是内容。它拒绝把二者混成“自动用户画像”，这正是它的克制之处。

## 7. 优点

- 避免了很多自动用户适配带来的误判和越界。
- 用户控制权强，设置逻辑清楚。
- 内容系统和用户设置系统边界干净。

## 8. 顾虑

- 如果目标是让 agent 深度贴合用户，这个项目提供的直接机制很少。
- 对工作习惯、能力状态、沟通风格等更深适配几乎没有支持。
- 不能把它误读成“成熟的 agent 用户自适应方案”。

## 9. 对 Aether 旧设计的挑战

| Aether 旧前提 | 是否被支持 / 挑战 / 补充 | 说明 |
| --- | --- | --- |
| 每个和记忆有关的系统都应自动学用户 | 挑战 | `memos` 证明很多产品宁可只给显式设置。 |
| 用户偏好与用户内容混在一起没关系 | 挑战 | 这里两者被严格分开。 |
| 自动适配比显式设置更先进 | 挑战 | 这个项目提醒我们，很多时候“克制”更对用户。 |

## 10. 对 Aether 的可能改变

### 10.1 用户需求理解的改变

- Aether 应先区分“用户要不要被自动学习”与“用户只想明示几个稳定偏好”。

### 10.2 产品流程的改变

- 可以先给用户显式、可编辑的设置和偏好入口，而不是默认走自动推断。

### 10.3 程序架构的改变

- 建议把“用户设置真源”和“从对话中抽出的适配记忆”分开建模。

### 10.4 只适合保留为启发的点

- `memos` 不提供完整 agent 自适配方案，但它对边界和可控性的坚持值得借鉴。
