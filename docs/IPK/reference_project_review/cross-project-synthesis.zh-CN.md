# reference_project：跨项目综合结论

> 状态：首轮全量审阅完成  
> 生成日期：`2026-04-18`  
> 覆盖项目：`graphify`、`graphiti`、`hermes`、`langgraph`、`letta`、`mem0`、`memos`、`openclaw`、`RecBole`、`recommenders`、`zep`

## 0. 先给结论

第一轮读完以后，最重要的结论不是“大家都在做 memory”，而是：

> 外部项目普遍把“用户自适应”和“记忆系统”视为强相关但不等价的两类问题；成熟项目通常会把二者拆成不同层次，再在产品流程里重新组合。

更具体一点：

- 强用户自适应项目，往往不只靠检索，还会有一层“始终在场的用户事实”。
- 强记忆项目，往往不只保存事实，还会严肃处理时间、失效、压缩、隔离、检索和真源问题。
- 推荐系统项目提醒我们：并不是所有用户适配都必须长成显式记忆。
- 工作区型个人助手项目提醒我们：并不是所有记忆都应该黑箱化自动学习。

## 1. 这 11 个项目大致分成了哪几类

### 1.1 用户自适应强、记忆也强

- `letta`
- `hermes`
- `openclaw`
- `zep`
- `mem0`（偏 memory substrate）

共同特点：

- 都承认用户长期事实会显著影响当前回答。
- 都不满足于只靠当前上下文窗口。
- 都在尝试把“总要知道的用户事实”和“临时要回忆的历史内容”分开。

### 1.2 记忆基础设施强，但不直接定义用户适配产品

- `langgraph`
- `graphiti`
- `graphify`

共同特点：

- 更关心状态保存、时间结构、图谱组织、durable execution、项目语料结构，而不是直接给出“怎么理解用户”的产品答案。
- 对 Aether 的启发主要在系统分层，而不是 UI 或产品话术。

### 1.3 用户适配很强，但主要是统计建模，不是 agent memory

- `recommenders`
- `RecBole`

共同特点：

- 证明“用户适配”可以主要是偏好建模、序列建模、上下文建模，而不需要显式长期记忆文件或记忆工具。
- 它们提醒我们不要把“个性化”自动等同于“记忆系统”。

### 1.4 几乎不做自动用户适配，但把用户知识资产做得很清楚

- `memos`

共同特点：

- 强调用户自有知识资产、可审计、可迁移、可控，而不是系统主动学习用户。

## 2. 跨项目重复出现的模式

## 2.1 “常驻核心区 + 按需召回区”反复出现

最明显的样本：

- `letta`：`human` / core memory 常驻，conversation / archival 按需检索
- `zep`：user summary 常驻，graph/context 按需取
- `hermes`：`USER.md` / `MEMORY.md` 常驻，session_search / provider recall 按需取
- `openclaw`：bootstrap files 常驻，memory_search / active memory 按需取

这对 Aether 的启发很强：

> 用户自适应不能只靠检索；至少有一层“始终在场的核心用户事实”是非常常见的成熟做法。

## 2.2 “短期历史”和“长期记忆”经常不是同一层

最明显的样本：

- `langgraph`：checkpoint vs store
- `hermes`：session_search vs `USER.md` / provider memory
- `openclaw`：session transcript vs `MEMORY.md` / daily notes / dreaming
- `graphiti`：episodes vs graph facts

这对 Aether 的启发也很直接：

> 当前会话历史、可搜索历史、长期稳定事实、可晋升知识，最好不要统称为同一个 memory。

## 2.3 “真源”和“检索索引”被明确区分

最明显的样本：

- `openclaw`：Markdown 文件是源，SQLite/向量库是派生索引
- `graphify`：原始语料/代码是真源，结构图谱是派生知识层
- `graphiti`：episode 真源，entity/edge 是图结构抽取结果
- `recommenders` / `RecBole`：交互数据和序列是真源，模型参数和矩阵是压缩表示

这对 Aether 的意义：

> 以后讨论 memory 时，必须明确“什么是可审计真源”“什么只是为了召回做的派生层”。

## 2.4 记忆系统越来越重视时间与失效，而不是只重视相似度

最明显的样本：

- `graphiti`：validity window、invalid_at、episode 时间结构
- `zep`：temporal knowledge graph
- `openclaw`：daily notes、temporal decay、dreaming
- 推荐系统：短期序列 vs 长期偏好

启发：

> 很多“记错了用户偏好”的问题，本质上不是检索差，而是时间建模差。

## 2.5 主动 recall 正在变成独立层

最明显的样本：

- `openclaw` 的 active memory
- `zep` 的 context engineering / user context
- `hermes` 的 prefetch_all + session_search guidance

启发：

> “模型自己会不会想起该回忆什么”不能完全靠运气；主动 recall 可能是独立可设计的一层。

## 3. 哪些 Aether 旧前提被反复挑战

## 3.1 “用户自适应可以主要靠检索”

被挑战。

因为多个成熟项目都显示：

- 只靠检索不够稳。
- 用户长期事实最好有核心常驻区。

## 3.2 “用户自适应和记忆系统几乎就是一回事”

被挑战。

因为外部项目大致呈现四种关系：

- 完全建立在记忆上：`mem0`、`letta`
- 有重叠但分层明显：`hermes`、`openclaw`、`zep`
- 主要是记忆基础设施，不定义用户适配：`langgraph`、`graphiti`、`graphify`
- 主要是用户适配，但不是 agent memory：`recommenders`、`RecBole`

所以更稳的说法应是：

> 用户自适应和记忆系统高度相关，但边界不固定，必须分开分析。

## 3.3 “长期记忆最好先设计成统一大系统”

被挑战。

因为外部项目多数都不是一个大而全的统一 memory，而是分层：

- 核心事实
- 日常/短期 notes
- session history
- 可搜索长期层
- 图谱/索引层
- 巩固/晋升层

## 3.4 “显式可编辑真源会让系统太笨”

被挑战。

`openclaw`、`hermes`、`memos` 都表明：

- 可编辑真源不但不会让系统失去能力，反而会大幅增强用户信任和治理能力。

## 3.5 “先把复杂层次都设计好，再等用户反馈”

也被挑战。

许多外部项目呈现的共同特点是：

- 真正稳定下来的结构，往往都对应了真实产品问题：
  - 上下文会爆
  - 多用户会串
  - 历史会忘
  - 偏好会变
  - 自动学习会误写

这说明复杂结构应该由具体问题倒逼，而不是先验铺开。

## 4. 对 Aether 用户自适应系统的阶段性启发

第一轮之后，更稳的用户自适应草图可能是：

1. 一层显式、可审计、相对稳定的核心用户事实区。  
2. 一层按需召回的历史互动区。  
3. 一层处理时间变化的机制，用来区分长期偏好与近期状态。  
4. 一套明确的纠正/撤销机制，避免临时表达固化。  
5. 如需更强能力，再叠加主动 recall，而不是一开始就把所有智能都塞进同一层。

更重要的是：

> Aether 不该再把“用户自适应”只理解成 profile schema 设计，而要把它看成“如何稳定、可控地让系统越来越懂当前这个用户”。

## 5. 对 Aether 记忆系统的阶段性启发

第一轮之后，更稳的记忆系统草图可能是：

1. 先定义真源。  
2. 再定义检索索引。  
3. 再定义短期到长期的晋升规则。  
4. 再定义压缩前保护和压缩后恢复。  
5. 最后才讨论是否需要更复杂的图谱或自动总结。

尤其值得注意的分层：

- 当前执行状态
- 当前会话历史
- 历史会话 recall
- 长期 curated memory
- 短期/每日 notes
- 派生索引 / 图谱 / 向量库

## 6. 目前最值得继续追问的问题

这些问题现在还不该拍板进 Aether 权威设计，而应作为第二阶段调研问题：

1. Aether 是否需要一层“始终在场的核心用户事实区”？  
2. 这层核心区的真源应该是什么：文件、数据库记录，还是别的？  
3. Aether 的“历史会话 recall”是否应与“长期记忆”分成两个明确子系统？  
4. 是否需要像 `openclaw active-memory` 那样的主动 recall 层？  
5. 是否需要像 `graphiti` 那样更认真地对待时间失效与事实更新？  
6. 是否要为用户适配和记忆分别定义纠错、撤销、审计边界？  
7. 是否要引入推荐系统视角，把长期偏好、短期序列、上下文状态分开建模，而不是只做一层 profile？

## 7. 这一轮最不该仓促做的事

基于这轮结果，现在最不该做的是：

- 立刻把某个外部项目方案整体照搬进 Aether。
- 为了维护旧设计而弱化外部证据。
- 还没完成第二轮专题调研，就回写 Aether 权威设计文档定死架构。

更合适的下一步应是：

- 以这份综合结论为导航，挑几个真正关键分歧点做第二轮专题调研。

## 8. 第一轮最终判断

如果只保留一句最重要的话：

> Aether 后续设计不该再把“用户自适应”和“记忆系统”混成一个模糊话题；更好的方向是先承认它们相关但不等价，再分别定义真源、边界、时间性、检索和纠错机制。
