# IPK：`piece` 与 `map` 的核心说明

这份文档专门解释 `IPK` 内容系统里最关键的两个部分：

- `piece`
- `map`

它不是新的技术方案，也不替代现有专题稿。  
它的目标更简单：

- 把这两个核心对象讲清楚
- 让内部讨论时更容易对齐
- 也让对外展示时更容易说明这套系统为什么可行

如果要用一句最短的话概括这两个对象的关系，可以写成：

> `piece` 负责把内容存成一个 AI 可用的长期对象。  
> `map` 负责在海量 `piece` 中把 AI 带到正确的位置。

---

## 1. 为什么 `piece` 和 `map` 是 IPK 的关键

`IPK` 不是普通笔记库，也不是传统意义上的文档检索系统。

它真正要解决的是两件事：

1. 怎样把想法、知识、讨论、反思、计划和项目材料，稳定地保存成一个可以被 AI 再次使用的长期对象。
2. 当这些对象越来越多之后，怎样让 AI 仍然能快速、准确、有结构地找到它们，而不是回到全库盲搜。

对应到系统设计里，这两个问题分别落在：

- `piece`
- `map`

所以可以把它们理解成两种不同但互相依赖的工程：

- `piece` 是内容工程
- `map` 是导航工程

没有 `piece`，IPK 就没有稳定内容对象。  
没有 `map`，IPK 就会在规模变大后失去检索质量和运行效率。

---

## 2. 先给一个整体图

高层上，IPK 的核心链路可以先理解成：

```text
原始输入
  -> 生成 piece
  -> 编译 surface 和 links
  -> 编译 maps 和 indexes
  -> 运行时按 map 路由
  -> 读取 piece 的 surface
  -> 必要时下钻正文
  -> 综合回答 / 复盘 / 联想
```

其中：

- `piece` 是内容对象本身
- `surface` 是 `piece` 暴露给 AI 的工作面
- `links` 是 `piece` 和其他 `piece` 的显式关系
- `map` 是从大量 `piece` 上面编译出来的导航层

所以这不是“两套平行系统”，而是一条完整链路里的两个关键节点：

- `piece` 决定系统“存得对不对”
- `map` 决定系统“找得快不快、准不准”

---

## 3. 什么是 `piece`

### 3.1 一句话定义

`piece` 是 `IPK` 里的统一最小长期内容单元。

它不是：

- 一段原始对话
- 一个临时 chunk
- 一条普通标签笔记
- 一个纯文本摘要

它更像是一张“长期内容对象卡片”，里面同时包含：

- 正文
- 身份信息
- 给 AI 用的工作面
- 与其他内容的关系

之所以选择 `piece` 作为统一最小单元，是因为它足够中性，能够统一承接很多不同类型的内容。

当前推荐的第一版类型包括：

- `idea`
- `knowledge`
- `thread`
- `review`
- `plan`
- `project`

这里最重要的一点是：

- `type` 表示这条内容是什么
- `status` 表示这条内容成熟到哪一步

例如：

- 一条内容可以是 `idea`
- 但它的 `status` 可能只是 `seed`

也可以是：

- 一条内容是 `knowledge`
- 但它的 `status` 已经是 `stable`

---

### 3.2 为什么 IPK 需要 `piece`

如果没有统一的 `piece`，系统很快会遇到几个问题：

#### 1. 内容对象会碎裂

系统会出现很多不同名义的小对象：

- 笔记
- 卡片
- 对话摘要
- 反思
- 计划
- 论文摘录

这样一来，后续很难做统一索引、统一检索、统一关系图。

#### 2. AI 不知道该把什么当成“可用对象”

如果内容只是一堆文件和聊天片段，AI 每次都得现场判断：

- 哪些是真正可用的内容
- 哪些只是原材料
- 哪些值得继续深入

成本很高，也不稳定。

#### 3. 后续地图和导航无法稳定编译

`map` 依赖的是稳定对象，而不是一堆无结构文本。

如果底层没有统一的 `piece`，上层地图只能退化成：

- 文件夹浏览
- 全文搜索
- 标签堆叠

这会让整个系统失去长期可扩展性。

所以 `piece` 的价值不只是“方便存东西”，而是：

- 它定义了 IPK 的最小工作对象
- 它让 AI 后续的检索、判断、联想都有稳定抓手

---

### 3.3 `piece` 的结构是什么样

当前最推荐的 `piece` 文件结构是：

```text
piece_xxx/
  piece.md
  meta.json
  surface.json
  links.json
```

这四部分缺一不可。

它们的职责可以概括成下面这张表：

| 文件 | 作用 | 主要面向 |
| --- | --- | --- |
| `piece.md` | 正文与内容真相层 | 人 + AI 最终下钻 |
| `meta.json` | 稳定结构身份证 | 系统 |
| `surface.json` | AI 工作面 | AI |
| `links.json` | 显式关系层 | AI + 系统 |

---

### 3.4 `piece.md`：正文层

`piece.md` 是内容真相层。

它保存的不是“为了检索而写的摘要”，而是这条内容真正想长期留下来的东西，例如：

- 原始想法
- 讨论整理
- 推导过程
- 研究判断
- 反思内容
- 未解决问题
- 后续补充

这层通常还会包含给用户审核的 `body_summary`。

它的作用不是提高第一轮检索效率，而是保证：

- 当系统真的需要证据和细节时，有一个可信的最终下钻层

换句话说：

- 地图不能替代正文
- surface 也不能替代正文
- 真正的内容和证据仍然要落在 `piece.md`

---

### 3.5 `meta.json`：结构身份证

`meta.json` 负责保存相对稳定的结构信息。

第一版最重要的字段包括：

- `id`
- `type`
- `title`
- `emoji`
- `created_at`
- `updated_at`
- `origin`
- `status`
- `domains`
- `methods`
- `contexts`
- `projects`
- `sources`

这些字段的意义可以简单理解为：

- `id`
  稳定主键
- `type`
  这条内容是什么类型
- `title`
  给人看的标题
- `origin`
  它从哪里来
- `status`
  它现在成熟到什么程度
- `domains / methods / contexts / projects`
  它属于什么领域、用了什么方法、处于什么语境、关联什么项目

这层最重要的特点是：

- 它偏稳定
- 它不承担正文细节
- 它也不直接承担复杂检索判断

它更像是这条内容的“结构身份证”。

---

### 3.6 `surface.json`：AI 工作面

`surface.json` 是 `piece` 设计里最关键的一层。

它不是普通摘要，而是 AI 在运行时使用这条 `piece` 的工作面。

当前推荐结构是：

```json
{
  "human": {
    "body_summary": "..."
  },
  "catalog": {
    "...": "..."
  },
  "retrieve": {
    "...": "..."
  },
  "associate": {
    "...": "..."
  }
}
```

这里最重要的思想是：

- 同一条内容，不同使用阶段需要不同粒度的信息
- 所以不能只给 AI 一层统一摘要

#### `human`

这是给用户看的审核层。

核心字段：

- `body_summary`

它的目标是：

- 让用户快速判断这条内容有没有表达对
- 让用户知道这条 piece 到底保留了什么

#### `catalog`

这是首轮筛选层，也是地图编译层。

核心字段包括：

- `summary`
- `domains`
- `methods`
- `projects`
- `contexts`
- `status`
- `salience`

它的特点是：

- 短
- 稳
- 有方向感

它主要负责：

- 第一轮候选筛选
- 地图编译
- 轻量列表展示

它不负责精确判断内容细节。

#### `retrieve`

这是精确检索层。

核心字段包括：

- `summary`
- `concepts`
- `problems`
- `questions`
- `claims`
- `assumptions`
- `open_questions`
- `keywords`
- `retrieval_hints`
- `role`

它的作用是：

- 判断这条 piece 是否真的与当前问题强相关
- 判断它该被当作证据、背景、方法还是启发
- 决定值不值得继续读正文

如果说 `catalog` 回答的是“值得先看谁”，  
那么 `retrieve` 回答的是“这条到底是不是强命中”。

#### `associate`

这是弱连接和联想层。

核心字段包括：

- `summary`
- `concepts`
- `methods`
- `problems`
- `association_hints`
- `bridge_targets`
- `link_glimpse`
- `association_risk`

它的作用是：

- 做类比
- 做方法迁移
- 做问题结构相似性的扩展
- 让系统具有“生命力”和跨主题连接能力

如果说 `retrieve` 负责精确命中，  
那么 `associate` 负责有控制的发散。

所以这两层一定不能混。

---

### 3.7 `links.json`：关系层

`links.json` 负责保存 piece 和其他 piece 之间的显式关系边。

它的结构大致是：

```json
{
  "links": [
    {
      "target": "piece_prev_a",
      "kind": "extends",
      "strength": 0.86,
      "reason": "延续了之前对 self-duality 的讨论"
    }
  ]
}
```

最重要的字段是：

- `target`
- `kind`
- `strength`
- `reason`

其中 `kind` 可以表达：

- `supports`
- `contradicts`
- `extends`
- `derived_from`
- `part_of`
- `uses_method`
- `answers`

等不同关系。

这层的意义是：

- 关系不再退化成标签堆
- 联想和图扩展有明确边类型可用
- 后续的关系图和关系地图可以建立在显式结构上

特别要强调的是：

- `reason` 非常重要

因为没有解释的关系图很容易变成噪音。

---

### 3.8 一个高质量 `piece` 应该满足什么

一个高质量 `piece` 至少应同时满足下面几件事：

#### 1. 正文层表达准确

也就是：

- 标题对
- `body_summary` 对
- `piece.md` 正文对

#### 2. 结构层稳定

也就是：

- `type` 合适
- `status` 合适
- `domains / methods / projects / contexts` 基本准确

#### 3. `catalog` 有方向感

也就是：

- 地图看到它时，知道它大致在讲什么
- 能分辨它大概属于哪个区域

#### 4. `retrieve` 有判断力

也就是：

- 系统能看出它是不是强相关
- 能看出它适合作为证据、背景、方法还是启发

#### 5. `associate` 有生命力

也就是：

- 它不是简单换种说法重复标签
- 而是真的能提供类比、迁移和桥接入口

#### 6. `links` 有解释

也就是：

- 不只是连上去
- 还要说明为什么连

所以高质量 `piece` 不是“正文好看就够了”，  
而是正文、结构、检索工作面和关系层都要成立。

---

### 3.9 `piece` 是怎么生成的

当前最推荐的生成链路是：

```text
select
  -> capture
  -> draft
  -> structure
  -> quality
  -> review
  -> commit
  -> reindex
```

各阶段可以简单理解成：

- `select`
  选中哪些输入值得进入 IPK
- `capture`
  提取原始内容和上下文
- `draft`
  生成标题、正文简介和正文草稿
- `structure`
  生成 `meta.json`、`surface.json`、`links.json`
- `quality`
  对关键字段做一轮 AI 自查和重写
- `review`
  用户主要审核标题、`body_summary` 和正文
- `commit`
  正式写入 piece
- `reindex`
  更新索引和地图

这里有两个非常关键的原则：

#### 原则 1：用户主要审核内容，不审核底层结构

默认情况下，用户主要审核：

- `title`
- `body_summary`
- `piece.md`

而不是被迫手填：

- `type`
- `methods`
- `retrieval_hints`
- `association_hints`
- `links`

#### 原则 2：生成后不能直接入库，要经过质量编译

也就是说，系统不能只做“字段生成”，还要做“字段质量编译”。

尤其是下面这些字段，必须重点打磨：

- `catalog.summary`
- `methods`
- `problems`
- `questions`
- `association_hints`
- `links.reason`

---

## 4. 什么是 `map`

### 4.1 一句话定义

`map` 是 `IPK` 的导航层。

它不直接保存正文真相，而是负责在海量 `piece` 里提供：

- 路由入口
- 候选区域
- 下潜方向
- 视角切换

如果说 `piece` 是内容对象，  
那么 `map` 就是“怎么走到这些内容对象”的路线系统。

最重要的一句话是：

> 地图负责引路，surface 负责判断，正文负责证实。

所以 `map` 不是答案层，不是摘要总集，也不是正文替代品。

---

### 4.2 为什么 IPK 需要 `map`

如果库里只有几十条 `piece`，也许简单搜索就够了。

但 IPK 的目标不是小规模临时资料夹，而是长期内容系统。

一旦 `piece` 数量上来，就会出现几个问题：

#### 1. 全库扫描太重

每次都直接看很多 `piece`，会导致：

- 成本高
- 速度慢
- 上下文膨胀
- 结果不稳定

#### 2. AI 不知道先从哪里下手

如果系统一上来面对的是海量内容对象，AI 很难自然地决定：

- 先按项目找
- 先按时间找
- 先按方法找
- 先按问题找

#### 3. 检索和联想会失去结构

没有地图时，系统很容易退化成：

- 关键词检索
- 向量召回
- 全局扩展

这会让强相关命中和弱联想混在一起。

所以 `map` 的存在，不是为了“看起来更高级”，而是为了让系统在规模变大后仍然能：

- 快
- 准
- 稳
- 有结构

---

### 4.3 `map` 的核心作用

`map` 主要做四件事：

#### 1. 提供入口

它告诉系统：

- 当前问题更适合从哪个维度进入

例如：

- 项目维
- 时间维
- 领域维
- 方法维
- 问题维
- 关系维

#### 2. 压缩搜索空间

它不让 AI 一上来就全库盲搜，而是先把注意力压缩到几个候选区域。

#### 3. 提供下潜路径

它不仅告诉 AI “先去哪看”，还告诉 AI：

- 下一步应该继续往下读
- 还是换一个视角

#### 4. 支持联想扩展

当系统不是只做精确检索，而是想找：

- 类似问题
- 类似方法
- 可能有桥接意义的旧内容

地图可以提供更好的扩展起点。

---

### 4.4 `map` 不是什么

为了避免把地图做歪，下面这几点必须写得非常清楚。

`map` 不是：

- 正文摘要全集
- 最终答案
- 直接证据层
- 一张贯穿所有层的万能总图

如果地图太轻，它就没有路由价值。  
如果地图太重，它就会冒充答案层，导致误判。

所以高质量地图的目标应当是：

- 高压缩
- 有方向感
- 可验证
- 可更新

---

### 4.5 `map` 的结构是什么样

和 `piece` 不同，`map` 目前还不是一个已经完全固定为单一 schema 的对象。

更准确地说：

- `piece` 已经有比较正式的文件结构和 schema
- `map` 现在更像一族编译产物

但即使如此，`map` 的结构还是可以清楚地说出来。

一个地图条目至少需要包含下面几类信息：

- 这是什么维度或什么区域
- 这个区域的一句压缩说明
- 下面有哪些值得继续看的候选对象
- 下一步更适合往哪里走

如果压成一个通用抽象，可以先这样理解：

```text
map
  -> metadata
  -> entries[]
       -> label
       -> summary
       -> dimension / scope
       -> candidate piece ids or child cluster ids
       -> optional salience / priority
       -> optional next-step hints
```

也就是说，地图本质上是“压缩后的区域入口集合”。

它的条目不是为了替你回答问题，而是为了告诉系统：

- 先看哪个区域
- 哪些候选值得先展开
- 下一步要继续下潜还是切换视角

---

### 4.6 `map` 有哪些类型

当前最明确的几类地图包括：

- 项目地图
- 时间地图
- 领域地图
- 方法地图
- 未解决问题地图
- 关系地图

对应到第一版索引与编译产物，可以落成：

- `by_type`
- `by_project`
- `by_time`
- `by_domain`
- `by_method`
- `open_questions`
- `graph_links`

这些可以理解为第一版静态地图。

除此之外，未来还会有动态地图，例如：

- 最近三个月里与当前问题最相近的 piece 区域
- 按当前问题重排后的方法簇
- 更适合这次提问先读的概念区

所以 `map` 至少可以分成两类：

#### 静态地图

特点：

- 按稳定维度重排
- 易缓存
- 易重编译

#### 动态地图

特点：

- 依赖当前问题
- 依赖当前上下文
- 更像运行时临时生成的路由图

---

### 4.7 `map` 是多层结构，不是一张图

IPK 不应该只有一张地图。

最推荐的层级理解是：

```text
L0  全局总地图
L1  维度地图（项目 / 时间 / 领域 / 方法 / 问题）
L2  主题簇地图
L3  局部邻域地图
L4  单个 piece 的 surface
L5  piece 正文
```

这意味着运行时的过程不是：

- 搜索一次
- 直接命中正文

而是：

1. 先选合适的地图
2. 再在该地图下找到候选区域
3. 再进入更低层的局部地图或候选列表
4. 再看少量 `piece` 的 `surface`
5. 必要时才下钻正文

所以 `map` 更像导航，而不是一次性搜索。

---

### 4.8 `map` 是怎么生成的

`map` 不是手工维护真数据，而是编译层。

当前最关键的设计原则是：

> 地图层主要消费 `catalog surface` 和少量聚合结果，  
> 不直接消费正文，也尽量不直接消费 `retrieve` 的长字段。

这条原则非常重要，因为它决定了地图的质量边界。

地图的推荐生成链路可以理解成：

```text
piece committed
  -> 读取 meta.json
  -> 读取 surface.catalog
  -> 读取 links.json 和少量聚合结果
  -> 重排 / 聚类 / 汇总
  -> 生成 maps 和 indexes
```

为什么主要基于 `catalog` 编译？

原因有三个：

#### 1. 保证地图轻量

如果地图直接吃正文，它会太重。

#### 2. 保证地图稳定

如果地图大量依赖 `retrieve` 长字段，它会越来越像伪答案层。

#### 3. 保证分工清楚

地图的职责是：

- 引路

不是：

- 代替 `retrieve`
- 代替正文

所以地图更适合由：

- `catalog.summary`
- `domains`
- `methods`
- `projects`
- `contexts`
- `status`
- `salience`

以及 links 和 open questions 的少量聚合结果编译出来。

---

### 4.9 运行时怎样用 `map` 做检索

当系统需要查 IPK 时，最推荐的链路是：

```text
问题
  -> 判断是否要查 IPK
  -> 选择优先地图
  -> 读取少量地图条目
  -> 锁定候选区域
  -> 读取候选 piece 的 catalog
  -> 收缩到少量 retrieve
  -> 必要时下钻正文
  -> 综合回答
```

这里最重要的是：

- `map` 不直接给答案
- 它只负责把系统带到正确区域

也就是说：

- `map` 决定“先看哪里”
- `retrieve` 决定“是否强相关”
- 正文决定“证据和细节到底是什么”

---

### 4.10 运行时怎样用 `map` 做联想

联想和精确检索不是同一件事。

如果目标是：

- 找启发
- 找类比
- 找方法迁移
- 找问题结构相似性

那么系统更适合这样走：

```text
问题
  -> 选择方法图 / 问题图 / 关系图
  -> 找到候选区域
  -> 读取候选 piece 的 associate
  -> 结合 links 做小范围扩展
  -> 输出启发和桥接方向
```

在这条链路里：

- `associate` 是主要工作面
- `link_glimpse` 和 `links.json` 是扩展边
- `association_risk` 用来控制发散强度

这条路径必须和精确检索路径区分开。

否则系统会把“弱连接启发”误当成“强事实命中”。

---

### 4.11 运行时的硬规则

为了让这套系统既快又准，运行时至少应遵守下面四条规则：

#### 1. 不能只根据地图回答

地图只能给候选方向，不能直接作为最终依据。

#### 2. 不能只根据联想结果回答

联想结果应明确标为：

- 启发
- 类比
- 弱连接

而不是强证据。

#### 3. 如果 `retrieve` 仍不足以判断，就必须继续读正文

这样可以防止：

- 表层看起来相关
- 实际正文并不支持

#### 4. 如果候选过多，应优先收缩，不要一口气扩展

否则系统容易重新掉回上下文膨胀。

---

## 5. `piece` 和 `map` 是怎样协作的

如果要把两者关系讲到最直白，可以这样说：

#### `piece` 解决的是“对象问题”

也就是：

- 这条内容怎样被稳定保存
- 怎样带有结构
- 怎样带有工作面
- 怎样带有关系

#### `map` 解决的是“路由问题”

也就是：

- 内容很多时先去哪里看
- 怎样避免全库盲搜
- 怎样在精确检索和弱联想之间切换

两者合起来，才构成 IPK 的核心能力：

- 先把内容做成可被使用的长期对象
- 再把这些对象组织成可导航、可路由、可验证的系统

---

## 6. 为什么这两部分决定了 IPK 的可行性和质量

### 6.1 如果 `piece` 做不好，会发生什么

如果 `piece` 质量不够，系统会出现：

- 正文表达不准
- `type` 和 `status` 混乱
- `catalog` 没有方向感
- `retrieve` 没有判断力
- `associate` 只是标签改写
- `links` 没有解释

这样一来，地图也会被劣质输入污染。

所以：

- 没有高质量 `piece`
- 就不可能有高质量 `map`

### 6.2 如果 `map` 做不好，会发生什么

如果地图做不好，系统会出现：

- 每次都要现扫很多 `piece`
- 上下文成本过高
- 检索和联想混在一起
- 回答看似相关但缺乏结构
- 系统规模一大就失去稳定性

所以：

- 没有高质量 `map`
- 就很难让高质量 `piece` 真正在运行时发挥作用

### 6.3 所以真正要同时成立的是什么

要让 IPK 成立，至少要同时满足：

#### 1. `piece` 足够结构化

让内容成为长期可用对象。

#### 2. `surface` 足够有判断力

让 AI 能分清：

- 强命中
- 弱联想
- 是否需要继续深入

#### 3. `map` 足够有方向感

让系统不用全库盲搜也能找到正确区域。

所以最终真正决定质量的不是某一个字段，而是这条链是否闭合：

```text
高质量 piece
  -> 高质量 catalog / retrieve / associate
  -> 高质量 map
  -> 高质量 runtime route
  -> 高质量回答 / 复盘 / 联想
```

---

## 7. 最适合展示时使用的三句话

如果需要非常简短地向别人讲解 IPK，可以直接用下面三句话：

1. `piece` 是 IPK 的最小知识对象，它把正文、结构、AI 工作面和关系边放进同一个长期对象里。
2. `map` 是 IPK 的导航系统，它不负责回答问题，只负责在多层、多维视角里把 AI 引到正确区域。
3. IPK 的核心不是“存很多内容”，而是“把内容做成可被路由、判断、验证和联想的系统”。

---

## 8. 一句话总结

`piece` 决定内容能不能被稳定保存和再次使用，  
`map` 决定这些内容在规模变大后还能不能被快速、准确、有结构地找到。

对 `IPK` 而言，这两者不是附属设计，而是整套系统成立的核心。
