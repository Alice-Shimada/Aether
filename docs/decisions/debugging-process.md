# 调试排查规则

## 已确认决定

- 从现在起，调试问题时默认先使用日志工具排查，不要一上来就改代码。
- 只有在日志、错误输出、调用链、运行态信息已经给出足够证据后，才进入代码修改阶段。
- 如果现有日志不足以定位问题，优先补充可回收、可验证的诊断日志或启用现有调试开关，再决定是否改实现逻辑。

## 适用范围

- 线上问题、联调问题、本地复现失败、回归缺陷、环境差异、配置异常、接口行为异常、任务执行失败。
- 适用于 CLI、服务端、前端、脚本、构建流程、集成链路与自动化任务。

## 默认排查顺序

- 先看已有日志、报错信息、堆栈、退出码、请求响应与时间线。
- 再确认复现步骤、输入条件、配置状态、环境差异与最近变更。
- 证据不足时，先增加或打开诊断日志、trace、debug 开关、观测命令。
- 只有当日志证据指向明确原因时，才修改代码、配置或测试。

## 执行约定

- 调试任务的第一次动作应优先是读取和分析日志，而不是直接提交补丁。
- 如果最终需要改代码，变更说明中应能对应到前面的日志证据或排查结论。
- 为排查临时加入的日志，在问题解决后应评估是否保留；无持续价值的诊断输出应移除或降级。
- 如果问题本质是缺少观测能力，应先补观测，再修问题。

## 通过标准

- 排查结论至少要回答：问题发生在哪里、证据是什么、为什么要这样修。
- 没有日志或等价运行态证据支持时，不应把猜测性改代码当成默认路径。
