# Aether 当前值得保留的部分、可能需要更改的部分与最高优先级判断

> 状态：已完成  
> 来源：基于 `2026-04-18-user-adaptation-memory-boundary` 本轮参考项目复审结果整理  
> 目的：沉淀“现在 Aether 用户自适应系统里哪些骨架值得保留”，以及“哪些地方有可能需要更改”，并明确“当前最需要优先处理的问题”。

## 0. 先给结论

这轮外部复审之后，Aether 用户自适应系统最不该推翻的，不是某个小机制，而是现在已经成形的这套主骨架：

- 三块架构
- confirmed habits 作为长期真源
- session scratch
- proposal review / human-in-the-loop
- 多作用域 scope
- 工作区层只存 refs 和轻量背景
- 当前 session active set
- v1 先以用户消息作为用户习惯主证据

同时，这轮复审也让一个问题变得非常突出：

> 当前架构最大的问题，不是“scope 不够多”或“proposal 不够强”，而是缺少一层明确、稳定、总是带上的用户层，导致系统虽然已经很会管理习惯，但还不够擅长在每轮运行时稳定地“知道这个用户是谁、应该怎么对待他”。

如果只再往前收一层优先级，那就是：

- 最值得保留的一点：用户适配真源必须可审计、可纠错、可撤销。
- 最值得优先修改的一点：尽快补出一层小而稳定、总是带上的用户层，不再主要依赖临时检索来决定系统该如何对待当前用户。

## 1. 当前最值得保留的东西（当前优点）

### 1.1 三块架构

这里指的是：

- 独立习惯库真源
- Aether 工作区引用层
- session 暂存区

这套结构值得保留，因为它已经提前避免了外部项目里最常见的一类问题：

- 长期真源和运行时状态混在一起
- 临时要求和长期习惯混在一起
- 用户画像、历史回忆、agent 经验混在一起

外部项目虽然术语不同，但大多都在强调同一件事：

- 长期真源
- 当前运行时
- 临时回忆/短期材料

不应该是同一个对象。

所以 Aether 现在把三块先拆开，是对的。

### 1.2 confirmed habits 作为长期真源

Aether 现在最值得保留的一点，是：

- 长期习惯必须有正式真源；
- 不能只靠每次临时从历史对话里重新猜。

外部项目里的对应物虽然不叫 confirmed habits，但本质上都有类似层：

- `USER.md`
- `user summary`
- `human block`
- 稳定 profile

这说明“正式长期真源”这件事本身没有问题。

Aether 当前的问题不是这层不该有，而是这层还没有被进一步压缩出一个更稳定的小型运行时用户层。

### 1.3 session scratch

session scratch 很值得保留。

它解决的是一个真实问题：

- 用户在当前对话里新说出的局部要求，不一定立刻该变成长期规则；
- 但系统又应该在当前 session 里先尊重它。

这个思路比“要么马上永久写入，要么完全不记”更稳。

外部项目有短期 memory、promotion、active memory，但像 Aether 这样把：

- 当前 session 暂存候选
- 长期 confirmed habits

明确分开，仍然是很有价值的。

### 1.4 proposal review / human-in-the-loop

这条主线值得继续保留，而且不建议轻易削弱。

原因很简单：

- 外部统一底座型方案虽然很强，但也更容易把错误长期写进去；
- Aether 当前场景里，用户对自己的习惯、偏好、长期规则更有判断权。

所以：

- AI 可以积极提取候选；
- AI 可以积极做去重、合并、作用域建议；
- 但高影响长期习惯，仍应以用户确认作为主结构。

这条路线与当前 Aether 的使用场景更匹配。

### 1.5 多作用域 scope

当前这套：

- `global`
- `subject`
- `initiative`
- `task_scope`
- `artifact`

很值得保留。

这轮复审后，它的价值反而更清楚了。因为外部项目反复说明：

- 不是所有习惯都全局适用；
- 不是所有长期信息都该以同一种范围生效；
- “长期有效”不等于“所有场景都要带上”。

外部项目里大多没有 Aether 这么明确的作用域表达，所以 Aether 这条路不是多余，而是更先进但还没完全用好的部分。

### 1.6 工作区层只存 refs 和轻量背景

`global_guidance / project_guidance / session binding` 这套工作区层设计值得保留，尤其是下面这条原则：

- 工作区层负责引用、缩范围、解释；
- 不复制长期真源正文。

这和外部成熟做法很一致：

- 运行时组织层不应直接等于长期真源层；
- 真源和运行时入口应分开。

所以工作区层不该退化成另一套习惯正文仓库。

### 1.7 当前 session active set

Aether 现在把“当前真正生效的习惯集合”单独看待，这一点很值得保留。

也就是：

- imported confirmed habits
- active scratch habits

共同构成当前 session 的生效集合。

这比很多系统里那种模糊的“系统大概会参考一些历史东西”要清楚得多。

以后无论补 `USER.md`、session recall 还是更宽记忆层，都最好不要丢掉这层“当前到底哪些规则真的在生效”的表达。

### 1.8 v1 先以用户消息作为用户习惯主证据

这个边界现在仍然值得保留。

注意，这不是说未来 assistant 输出不能进入任何长期记忆，而是说：

- 在用户自适应系统本身里，
- 长期用户习惯真源先以用户侧证据为主，
- 这是一个合理、谨慎、现在仍然稳的起点。

外部项目支持未来扩展更宽记忆来源，但没有足够证据支持 Aether 现在就把 assistant 输出直接并入用户习惯真源。

## 2. 为什么这些东西值得保留

把上面几条放在一起看，Aether 现在真正有价值的地方是：

- 它已经很认真地区分“长期真源”和“当前运行时”
- 它已经很认真地区分“临时候选”和“正式习惯”
- 它已经很认真地区分“适用范围”
- 它已经很认真地保留了用户确认权

这说明当前系统的主问题不是“骨架完全错了”，而是：

- 运行时用户层还不够清楚；
- 更宽记忆层还没接进来；
- session recall 还没有单独站稳；
- 因此当前系统更像“很会管理习惯”，但还不够像“每轮都稳定懂用户”的完整运行时架构。

## 2.1 当前保留项里的最高优先级

如果要在“值得保留”的点里只选一个优先级最高的，我会选：

> 用户适配真源必须可审计、可纠错、可撤销。

原因不是它技术上更花哨，而是它决定了 Aether 和很多“自动学习你”的系统到底有什么根本差别。

这条一旦丢掉，就会直接带来三类风险：

- 用户很难知道系统为什么这样理解自己；
- 错误长期写入后，修正成本会明显上升；
- 后面即使补进更强记忆能力，信任感也会下降。

所以这条更像产品底线，而不是普通实现偏好。

## 3. 当前可能需要更改的东西（当前缺点 / 可改项）

### 3.1 缺少稳定用户层

这是当前最明显、也最值得优先改进的地方。

外部项目反复给出的现实样本是：

- 稳定用户层通常会被压缩成一个很小、很稳定、默认常驻的块；
- 它不等于全部长期记忆；
- 但它会直接决定主回答的行为和说话方式。

而 Aether 现在虽然已经有：

- confirmed habits
- scope
- proposal
- scratch
- active set

却还没有把“默认总是带上的稳定用户层”真正独立出来。

这意味着：

- 系统已经很会管理习惯；
- 但还不够会在每轮开始时稳定地“先知道这个用户是谁”。

### 3.2 目前更像“习惯管理系统”，还不够像“稳定运行时用户系统”

这不是说当前设计错了，而是说重心有一点偏。

现在的 Aether 更擅长：

- 提取候选习惯
- 审核长期习惯
- 管理作用域
- 区分长期和临时

但从运行时视角看，还缺少一个非常直接的入口来回答：

- 这位用户最稳定的几条长期偏好是什么？
- 哪几条应该每轮默认带上？
- 哪些只该按需召回？

所以当前系统的短板不是“不会存”，而是“默认怎么稳定地用”还不够清楚。

### 3.3 session recall 还没有单独站稳

这轮复审后，一个越来越清楚的问题是：

- “过去聊过什么”
- “这个用户通常喜欢怎样被对待”
- “正式知识材料里写了什么”

这三件事不应该继续混在一起讨论。

如果 session recall 不单独成层，后面就容易出现：

- 某次历史对话被误当成长期用户习惯
- 某条项目上下文被误当成正式知识真源
- 运行时不知道是在“查用户画像”，还是在“翻旧对话”

所以它现在至少应该在架构讨论中被单独看待。

### 3.4 未来通用记忆不应先走“大共享池”路线

这轮复审最明确的一条提醒是：

- 未来如果要做更宽通用记忆，
- 更稳的方向是“统一编排层 + 分层真源”，
- 而不是先做一个把所有东西都丢进去的大而全共享池。

这意味着 Aether 未来需要避免：

- 用户稳定信息、历史会话、assistant 输出、任务材料、agent 经验全混入一个池子；
- 存的时候不分层，结果用的时候也很难解释；
- 改错、删除、追责时，不知道该改哪一层。

### 3.5 主动召回还值得单独设计

外部项目已经说明：

- “系统有检索能力”
- 和
- “系统会在该回忆的时候主动回忆”

不是一回事。

如果只把一切都交给模型临时去搜，就会出现：

- 有工具，但不一定触发；
- 触发了，但时机太晚；
- 搜到了，但没有成为主回答前置条件。

所以 Aether 后面需要单独回答一个问题：

- 哪些用户信息、历史对话、长期材料，应该在主回答前被主动预召回？

### 3.6 这些“可改项”不等于当前骨架应该推翻

这部分更准确的含义是：

- 当前骨架整体是对的；
- 但运行时层次还不够完整；
- 有几个关键层还没有被真正命名清楚、边界清楚、优先级清楚。

所以这些是“值得继续补强的缺口”，不是“现有方向整体失败”的证据。

## 3.7 当前可改项里的最高优先级

如果要在“可以修改”的点里只选一个优先级最高的，我会选：

> 尽快补出一层小而稳定、总是带上的用户层。

它的重要性高于“是否继续扩 scope”“是否放宽证据来源”“是否立刻接入更宽通用记忆”，因为它会先影响最直接的运行时体验：

- 系统是否每轮都能稳定知道这个用户是谁；
- 哪些用户信息应该默认进入主回答；
- 后面接 session recall 和更宽记忆层时，运行时装配有没有一个清楚锚点。

换句话说，当前不是“不会存”，而是“默认怎么稳定地用”还不够清楚。

## 4. 当前最大架构问题

### 4.1 一句话版本

当前最大架构问题是：

> Aether 现在已经比较擅长“管理和存放习惯”，但还没有形成一层明确、稳定、低成本、总是带上的用户层，因此运行时仍然偏依赖临时匹配，而不是稳定地把“这个用户是谁、长期该怎么对待他”压缩成一个小而强的默认入口。

### 4.2 这个问题具体是什么意思

现在 Aether 已经有：

- confirmed habits
- scope
- proposal
- scratch
- active set

这些都很重要。

但外部复审显示，多数成熟系统在这些东西之外，还会再抽出一层很关键的结构：

- `USER.md`
- `user summary`
- `human block`
- `persona/human` 常驻块

这层的特点是：

- 很小
- 很稳定
- 不放太多杂项
- 每轮都默认带上
- 直接影响主回答的风格和行为

而 Aether 当前还没有把这层真正独立出来。

结果就是：

- confirmed habits 虽然存在，但更像“长期习惯库”
- 工作区 guidance 虽然存在，但更像“缩范围和引用入口”
- session active set 虽然存在，但更像“运行时集合”

可系统还缺一个非常明确的中间层，来回答：

- 这位用户最稳定的几条长期偏好是什么？
- 这几条信息是否每轮都应该默认带上？
- 它们和更宽的记忆、历史会话、通用习惯之间是什么关系？

### 4.3 为什么这是最大问题

因为如果没有这层，系统会出现三个后果：

第一，运行时稳定性不够。

- 有些真正重要的用户信息，本来应该每轮都带着；
- 现在却可能每轮都要重新匹配、重新决定。

第二，系统边界不够清楚。

- confirmed habit library 是长期真源；
- 但哪些真源应该“总是直接进 prompt”，哪些只该按需召回，当前还没有被很明确地切开。

第三，后面很难优雅地接更宽通用记忆。

如果未来 session recall、task memory、agent memory、environment memory 都进来，但还没有一个稳定用户层做锚点，就很容易把运行时装配做得越来越乱。

### 4.4 这个问题不等于什么

它不等于：

- 当前三块架构错了
- confirmed habits 不该存在
- scope 太复杂
- proposal review 太重

恰恰相反。

当前这些骨架都值得保留。

真正的问题是：

- 在这些骨架之上，
- 还缺一个“稳定用户层”的运行时落点。

## 5. 当前不应误判成“最大问题”的东西

这轮复审后，下面这些不应被误判成当前最大的架构问题：

- `scope` 太多
  当前更大的问题不是作用域过多，而是稳定用户层还没独立出来。

- proposal review 太保守
  当前更大的问题不是 review 太重，而是没有一个小而稳的用户层把真正重要信息固定下来。

- session scratch 太复杂
  scratch 反而是当前很合理的部分，不是首要矛盾。

- 当前只看用户消息证据太窄
  这确实是未来会扩展的边界，但现在还不是最核心架构矛盾。

## 6. 下一步讨论最应该围绕什么展开

如果以后继续讨论这个文档，最值得优先讨论的是：

1. Aether 的稳定用户层是否应先做成一个 `USER.md` 视图。
2. 这层是独立真源，还是 confirmed habits 的压缩编译结果。
3. 这层和 active scratch、confirmed habits、session recall、未来通用记忆之间的优先级。
4. 这层的更新方式：
   - 自动提议
   - 用户确认
   - 手工编辑
   - 周期性重写
5. 这层应该默认承载哪些内容，不应该承载哪些内容。

## 7. 当前建议

基于这轮复审，当前最稳的路线不是推翻现有骨架，而是：

- 保留当前三块架构和 confirmed habits 主线；
- 尽快补一个稳定用户层；
- 以后把 session recall 和更宽通用记忆层作为平行层继续接入；
- 让运行时装配从“习惯匹配系统”走向“稳定用户层 + 按需召回层 + 临时活跃层”的组合系统。

## 8. 最后压成一句话

如果只保留一句最短判断，那就是：

> Aether 现在最该保住的是“可审计、可纠错、可撤销的用户适配真源”，最该优先补的是“稳定用户层”，这样它才不会一直停留在“会管理习惯”，而能真正稳定地“懂这个用户”。
