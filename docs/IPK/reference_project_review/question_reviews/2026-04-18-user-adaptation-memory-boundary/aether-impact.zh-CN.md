# 用户自适应系统与记忆系统边界：Aether 影响分析

> 状态：已完成

## 0. 适用范围

- 本文只记录本轮复审对 Aether 的影响，不提前把不稳定判断写成正式架构约束。
- 当前不直接改写 `implementation-decisions` 或 `open-questions` 权威文档，只提出稳定度分级建议。

## 1. 可以立即吸收的实现技巧

- 运行时应明确区分“稳定用户层”和“更宽记忆层”。
  这点同时得到 `zep`、`hermes`、`openclaw`、`letta` 支持。
- 即使不新增完整 memory subsystem，也应把“总是该带上的用户信息”做成一个小而稳定的编译结果。
  这可以是 `user summary`、`USER.md` 视图、或 current context packet 里的独立分区。
- 如果未来要做更宽的通用记忆，优先采用“统一编排层 + 分层真源”，而不是先做一个大而全共享池。
  `hermes`、`openclaw` 给了更稳的现实样本。
- 主动召回值得单独看待。
  `openclaw active memory` 说明“会搜索”与“会在该回忆时回忆”不是一回事。

## 2. 需要重新讨论的产品假设

- 当前 Aether 是否过度把“用户自适应系统”和“记忆系统”理解成二选一。
  这轮复审更支持“强耦合分层”，不支持“完全合并”或“几乎完全独立”。
- 当前 v1 把用户适配 evidence 主要限制在用户消息，这一前提不必马上推翻，但其表述应更精确：
  - 用户习惯真源仍应以用户侧证据为主；
  - 更宽记忆层可在未来吸收 assistant 输出与任务结果。
- 当前用户自适应系统若长期没有“稳定用户层”，会与多数成熟样本偏离。
- 当前 open question 里“程序性技能层要不要独立”被这轮进一步强化了。
  `hermes`、`openclaw` 都说明“用户是谁”和“这类任务通常怎么做”最好不要长期混写成同一种记录。

## 3. 目前还不建议改写的权威结论

- `implementation-decisions` 里“三块架构”仍然可以保持。
  这轮复审并没有推翻“独立习惯库 / 工作区引用层 / session 暂存区”的主结构。
- “v1 自动提取快链路只看当前 session 的用户消息”暂时也不建议直接改写。
  外部项目支持未来扩展通用记忆来源，但不足以让 Aether 立刻放弃当前谨慎边界。

## 4. 需要实验验证的问题

- Aether 是否需要一层像 `user summary` / `human block` / `USER.md` 那样的稳定用户层。
  实验重点：它是否能降低每轮检索成本、提高风格稳定性。
- 通用记忆层若吸收 assistant 输出，是否会污染用户适配。
  实验重点：哪些 assistant 产物适合入库，哪些只该留在会话回忆。
- 是否需要把 session recall 单独成层，而不是继续混在 adaptation 或 IPK 里讨论。
  这点受到 `hermes`、`openclaw`、`langgraph` 一致支持。

## 5. 暂不适合 Aether 的外部做法

- 暂不适合直接照搬 `mem0` / `letta` 那种高度统一底座。
  原因不是它们不好，而是 Aether 当前的人审、作用域、纠错优先级更高，若过早统一，污染治理成本会过大。
- 暂不适合把 `graphiti` 直接当成用户适配主架构。
  它更擅长统一事实和时间演化，不足以单独承担稳定行为控制层。
- 暂不适合把推荐系统式隐式建模直接照搬为 v1 主结构。
  这类路线解释性和用户可控性偏弱，不符合 Aether 当前产品心智。

## 6. 当前建议

本轮最稳的 Aether 建议不是“合并”或“分开”二选一，而是：

- 长期真源保持分层；
- 运行时装配做强耦合；
- 用户适配只带稳定高价值信息；
- 更宽记忆层留给未来的 session recall / task memory / agent memory / environment memory。
