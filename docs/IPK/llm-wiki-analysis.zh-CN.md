# `LLM Wiki` 案例解读：它怎么做、和 IPK 有何异同、哪些值得借鉴

这份文档用于解读 [llm-wiki.md](/home/bzz/Aether/docs/IPK/llm-wiki.md)，并把它和当前的 [IPK 内容系统](/home/bzz/Aether/docs/IPK/01-ipk-content-system/ipk-content-system-readme.md) 放在同一张图里理解。

它主要回答三件事：

- 这个案例到底在讲什么，以及如果把它当成一个项目思路，它是怎么做的
- 这个案例和当前 IPK 内容系统的异同
- 哪些值得借鉴，哪些不适合直接照搬

## 1. 先说结论：这其实不是一个“成品项目”，而是一种模式文档

`llm-wiki.md` 严格来说不是完整实现说明书，而是一份 idea file。

它的作用不是给出精细后端架构、数据库 schema 或 API 设计，而是向 LLM 传达一个高层模式：

- 不要每次问问题都回到原始文档里重新检索和拼装
- 而是让 LLM 持续维护一个长期存在的 wiki
- 这个 wiki 位于“原始材料”和“最终回答”之间
- 它会随着新材料和新问题不断更新，因此形成复利积累

如果用一句最直白的话来概括它：

> `LLM Wiki` 想做的是一层“由 LLM 持续维护的中间知识层”，而不是一次性的问答检索层。

## 2. 这个案例如果当成一个项目思路，它是怎么做的

### 2.1 基本结构

它把系统分成三层：

- `Raw sources`
  原始资料层。文章、论文、图片、数据文件等，保持不可变，是源头真相。
- `Wiki`
  由 LLM 维护的一组 markdown 页面。包括摘要页、主题页、实体页、比较页、总览页、综合页等。
- `Schema`
  一份写给 LLM 的维护规约。告诉它 wiki 怎么组织、怎么 ingest、怎么 query、怎么 lint。

也就是说，它的基本思路不是：

- 上传文档
- 问问题时临时 chunk 检索
- 再现场生成答案

而是：

```text
raw sources
  -> LLM ingest and maintenance
  -> persistent wiki
  -> query against wiki
  -> useful outputs filed back into wiki
```

### 2.2 三类核心操作

#### `Ingest`

当你加入一个新来源时，LLM 会：

- 阅读来源
- 和你讨论重点
- 写一个或多个新 wiki 页面
- 更新已有主题页与实体页
- 更新总索引
- 追加一条操作日志

它强调的一点是：

- 一份新来源不只是“被索引”
- 而是“被整合进现有知识结构”

#### `Query`

当你提问时，LLM 会：

- 先查 wiki，而不是直接回原始文档堆里重找
- 读取相关页面
- 综合后生成回答

它还特别强调：

- 好的回答不应该消失在聊天记录里
- 而应该回写成新的 wiki 页面

所以问答本身也会继续积累知识。

#### `Lint`

它建议定期让 LLM 给整个 wiki 做健康检查，重点看：

- 页面之间是否出现矛盾
- 旧结论是否已被新来源推翻
- 有没有孤儿页
- 有没有该有但还没建的主题页
- 有没有缺失的交叉引用
- 还缺哪些值得继续查的新问题和新来源

这一步很关键，因为它把“长期维护”显式化了。

### 2.3 两个辅助文件：`index.md` 和 `log.md`

它认为 wiki 变大以后，至少要有两个辅助文件：

- `index.md`
  内容导向的总目录，按类别列出页面、链接、一句话摘要、可选元数据。
- `log.md`
  时间导向的追加日志，记录 ingest、query、lint 等发生了什么。

它们的作用不同：

- `index.md` 帮助“从哪里开始找”
- `log.md` 帮助“最近做过什么、系统怎么演化到现在”

### 2.4 它默认的人机分工

这个案例的人机分工非常清楚：

- 人负责找资料、提问题、判断重点、决定探索方向
- LLM 负责摘要、改写、交叉引用、更新页面、补记账务性工作

它最核心的信念是：

- 人不是不愿意思考
- 人是不愿意做大量重复维护工作

### 2.5 它默认的工具环境

这份文档明显假定了一个偏本地 markdown 工作流：

- 用 Obsidian 浏览页面和图谱
- 用 git 管理 markdown 仓库
- 需要时加本地搜索工具，比如 `qmd`
- 需要时用 Dataview、Marp 之类插件或输出格式

所以它更像：

- “LLM 维护一个 markdown wiki 仓库”

而不是：

- “一个已经定义清晰后端领域模型和运行时检索链路的应用系统”

## 3. 它和 IPK 的异同

### 3.1 共同点

这两个方向其实非常接近，至少在核心理念上高度一致。

共同点主要有：

- 都不满足于一次性 RAG，都强调长期积累
- 都认为 AI 不应只在提问时检索，而应持续整理和维护知识结构
- 都把“编译出的中间层”看得比“临时全文检索”更重要
- 都强调交叉引用、综合、更新，而不是只做文件堆放
- 都默认人负责内容和方向，AI 负责结构与维护
- 都接受“好问题和好回答也可以成为知识库的一部分”

如果只看精神内核，`LLM Wiki` 和 IPK 是同一条路上的两个版本。

### 3.2 关键差异

| 维度 | `LLM Wiki` | 当前 IPK |
| --- | --- | --- |
| 系统定位 | 持续维护的个人 wiki 模式 | 长期内容系统与运行时认知底座 |
| 核心单元 | wiki page | `piece` |
| 主要内容对象 | 外部资料、主题页、实体页、综合页 | 想法、知识、讨论、反思、计划、项目片段 |
| 结构分层 | `raw sources / wiki / schema` | `piece.md / meta.json / surface.json / links.json / maps / indexes` |
| 关系表达 | 主要靠页面之间的链接与页面更新 | 显式 `links.json`，带 `kind / strength / reason` |
| 检索主链 | `index -> relevant pages -> answer` | `maps -> catalog -> retrieve / associate -> body` |
| 运行时目标 | 主要服务“对 wiki 的问答与浏览” | 还要服务普通问答后台自动调用 |
| 用户审核边界 | 倾向于让 LLM 直接维护 wiki | 明确强调用户主要审核标题、`body_summary`、正文 |
| 健康维护 | 显式提出 `lint` | 已提出 `quality`、`periodic review`，但还没有单独命名成类似 wiki lint 的显式工作流 |
| 工程假定 | 本地 markdown 仓库、Obsidian、git | Aether 内部 route、provider、session prompt、global sync |
| 精确检索与弱联想的区分 | 相对弱，更多靠页面结构与人工浏览 | 明确区分 `retrieve` 和 `associate` |

### 3.3 总体判断

如果把二者关系说得更直白一点：

- `LLM Wiki` 更像一个非常优秀的高层模式原型
- IPK 则是在同一方向上，走得更细、更强结构化、更偏运行时系统化的一版

也就是说：

- `LLM Wiki` 给了你一个很好的方向感
- IPK 已经把很多在 `LLM Wiki` 里还是隐性的东西，拆成了正式对象和正式流程

## 4. 哪些地方值得借鉴

下面这些点，我认为非常值得从 `LLM Wiki` 吸收到 IPK 中。

### 4.1 把“原始材料层”进一步显式化

`LLM Wiki` 很强调：

- 原始材料不可变
- 中间 wiki 是编译产物

这对 IPK 很有价值，因为你现在已经有：

- `piece`
- `meta.sources`
- 外部导入与溯源意识

但还可以继续加强成更明确的“raw layer”概念。

适合借鉴成：

- 更稳定的原始材料目录
- 更正式的 source registry
- 更清楚的“原始来源 vs 编译产物”边界

### 4.2 把 `lint` 做成一等工作流

`LLM Wiki` 非常值得借鉴的一点是：

- 它没有把维护当成隐含动作
- 而是显式提出了 `lint`

这对 IPK 的启发是：

- 除了 `ingest` 和 `query`
- 还应该有一条明确的 `ipk-lint` 或 `ipk-review` 维护链

它可以专门检查：

- `contradicts`
- `superseded`
- 孤立 piece
- 缺失 links
- 该有但还没形成的综合 piece
- 该补但还没补的 open questions

### 4.3 把“追加日志”做出来

`log.md` 是一个很朴素但很有力的设计。

它能补上 IPK 目前相对弱的一面：

- 你现在的空间结构很强
- 但“时间上的系统演化记录”还不够显式

这个思路适合借鉴成：

- ingest 日志
- revise 日志
- lint 日志
- reindex 日志
- 关键 query / synthesis 日志

这样以后系统不仅知道“库里有什么”，还知道“最近发生了什么”。

### 4.4 把高价值问答回写成长期内容

`LLM Wiki` 很强调：

- 好问题产生的好答案，不应消失在聊天里

这点和 IPK 非常相容。

在 IPK 里，它不一定要回写成 wiki page，但很适合回写成：

- `review`
- `knowledge`
- `thread`
- `project` 相关 piece

这能直接增强 IPK 的复利性。

### 4.5 显式维护少量“高层综合对象”

`LLM Wiki` 的实体页、主题页、综合页，虽然没有你现在这么正式的 `piece` 设计，但它提醒了一件很重要的事：

- 长期系统不只需要原子内容
- 也需要持续被改写的高层综合对象

对 IPK 来说，这意味着未来很适合显式维护：

- 项目综述 piece
- 主题综述 piece
- 阶段回顾 piece
- 问题簇综合 piece

它们不是替代普通 piece，而是站在普通 piece 之上的“持续综合层”。

### 4.6 做一份更短、更操作性的维护规约

`LLM Wiki` 里 `schema` 的角色很重要。

它提醒你：

- 不是只有正式设计文档才有价值
- 还应该有一份更短的、直接写给 agent 的维护规约

IPK 现在的设计文档已经很强，但比较分散、比较完整，未必最适合直接驱动某个 agent 的日常操作。

适合借鉴成：

- 一份短版 `ipk-maintainer` 规约
- 或一组清晰的 `ipk-capture / ipk-route / ipk-retrieve / ipk-lint / ipk-synthesize` 执行说明

### 4.7 先用简单视图，再逐步补复杂工具

`LLM Wiki` 的态度很克制：

- 小规模时先靠 `index.md`
- 规模大了再补搜索工具

这对 IPK 的启发不是“回退到 index-only”，而是：

- 第一版先把最有价值的编译视图做对
- 不要太早被复杂检索基础设施绑住

也就是说，先把：

- maps
- indexes
- surface 质量

做好，依然是正确路线。

## 5. 哪些地方不适合直接照搬

下面这些点我认为不能直接照搬，否则会把 IPK 拉回一个更粗糙的模式里。

### 5.1 不能把 IPK 扁平化成普通 wiki page 集合

`LLM Wiki` 的核心单元是页面，这在很多场景里足够好。

但 IPK 已经明确选择了：

- `piece`
- `meta`
- `surface`
- `links`
- `maps`

这套分层比普通 wiki page 更适合：

- 运行时路由
- 精确检索
- 弱联想
- 自动问答接入

所以不能为了贴近案例而退回到“全都写成一页 markdown”的模型。

### 5.2 不能只靠 `index.md` 一层导航

`LLM Wiki` 的 `index.md` 很有用，但它主要适合：

- 中等规模
- 以浏览和手动查询为主

IPK 的目标更大，也更偏系统运行时。

所以你不能把：

- `多张地图`
- `多层导航`
- `catalog / retrieve / associate`

压缩回一个统一目录页。

### 5.3 不能只靠 markdown 链接表达关系

`LLM Wiki` 里的关系主要靠页面互链和页面更新维护。

但 IPK 明确需要的是：

- typed links
- link reason
- 强弱区分
- 关系图扩展

所以不能让普通双向链接替代 `links.json`。

### 5.4 不能默认让 LLM 完全拥有“内容真相层”

这是一个非常重要的差异。

`LLM Wiki` 主要处理的是：

- 外部文档
- 主题整理
- 资料综合

而 IPK 很多时候记录的是：

- 你自己的想法
- 你的研究直觉
- 你的问题意识
- 你的阶段性判断

这意味着在 IPK 里：

- LLM 可以主导结构
- 但正文层仍然应保留清晰的用户审核边界

所以 `LLM Wiki` 那种“LLM 完全写、用户主要浏览”的默认姿态，不适合直接照搬到 IPK 的所有对象上。

### 5.5 不能把 Obsidian 浏览体验当成主产品假设

`LLM Wiki` 默认的使用图景很大程度上是：

- Agent 在一边维护
- 人在 Obsidian 里浏览

这没有问题，但 Aether 的目标不是做一个附着在 Obsidian 上的工作流。

IPK 需要的是：

- 后端服务
- 前端 provider
- session 内自动调用
- 事件流同步

所以 Obsidian、Dataview、Graph View 更适合当作灵感来源，而不是产品主架构。

### 5.6 不能把它理解成“文档资料整理系统”就够了

`LLM Wiki` 很强的一面是文档导向。

但 IPK 的范围更广，至少还包括：

- 会话内容
- 想法碎片
- 讨论整理
- 反思
- 计划
- 项目片段

所以如果直接按 `LLM Wiki` 的文档中心视角来做，IPK 会丢掉你最独特、也最重要的部分。

## 6. 我最推荐的吸收方式

如果要把这个案例真正转化成 IPK 的增益，我最推荐的吸收顺序是：

1. 保留 IPK 现有 `piece / surface / maps` 主骨架，不回退成普通 wiki 模式。
2. 补强“原始材料层”与来源注册，让“source of truth”更清楚。
3. 新增显式的 `lint / health check / periodic maintenance` 工作流。
4. 新增追加式操作日志，让系统拥有时间维度的自我记录。
5. 允许高价值 query / synthesis 结果回写成新的长期 piece。
6. 逐步形成少量高层综合对象，而不是只有原子 piece。
7. 最后再考虑搜索工具、图谱浏览、Dataview 风格视图等外围增强。

## 7. 一句话总结

`LLM Wiki` 最值得你借鉴的，不是“把所有内容做成 wiki 页面”，而是下面这件事：

> 在原始材料和最终回答之间，建立一层由 AI 持续维护、持续更新、持续积累的中间知识层。

而 IPK 的价值，则在于你已经把这层中间知识层进一步推进成了：

- 更细颗粒度的 `piece`
- 更清楚的 `surface` 分层
- 更正式的关系表达
- 更适合运行时调用的导航系统

所以最好的吸收方式不是照搬，而是：

- 吸收它的长期维护思想
- 保留你自己的结构化和系统化优势
