# IPK 术语表（中文）

这份文档用于解释 `IPK` 文档体系中反复出现的专有名词。

它主要解决一个阅读问题：

- 当你第一次读总览稿、细节稿或规划稿时，会看到很多像 `piece`、`surface`、`retrieve`、`associate`、`signal`、`policy` 这样的词
- 这些词单独出现时，未必能立刻知道它们在项目里到底指什么

所以这份术语表不追求学术定义，而是只回答两件事：

1. 这个词在 `IPK` 里是什么意思
2. 这个词在系统里承担什么角色

---

## 1. 怎么使用这份术语表

阅读时可以把术语分成三类：

- 共通工程词
  例如 `schema`、`runtime`、`route`
- `IPK` 内容系统词
  例如 `piece`、`surface`、`map`、`retrieve`
- 用户自适应系统词
  例如 `signal`、`proposal`、`profile`、`policy`

如果你只是第一次读 `overview`，最推荐优先看下面这些词：

- `piece`
- `surface`
- `catalog`
- `retrieve`
- `associate`
- `links`
- `map`
- `signal`
- `proposal`
- `policy`

## 2. 共通工程词

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `schema` | 一组结构规则、字段约束和生成规范 | 规定对象应该长什么样 |
| `compiler` | 把原始内容编译成结构化产物的模块或步骤 | 把“原材料”变成“系统可用对象” |
| `runtime` | 真正回答问题或执行任务时发生的调用阶段 | 决定系统当下怎么使用长期信息 |
| `route` | 运行时决定“先查哪里、再查哪里”的路由动作 | 控制查找路径，避免全局盲搜 |
| `index` | 为检索和导航预先生成的结构化视图 | 帮系统快速定位候选对象 |
| `view` | 面向某种浏览或导航目标的组织方式 | 提供一个特定角度的入口 |
| `scope` | 一条记录、规则或习惯适用的范围 | 决定它应在全局、学科、任务、产物还是当前会话中生效 |
| `worktree` | 当前项目实际工作的文件树或 Git 工作副本 | 给 Aether 判断当前文件、目录和项目边界 |
| `ingest` | 把原始输入纳入系统的过程 | 完成捕获、整理、结构化和入库 |
| `review` | 对生成结果做检查、确认或重写的过程 | 控制长期层写入质量 |
| `stash` | 把当前 review 结果存成可重开的工作草稿 | 保留草稿而不正式入库 |
| `discard` | 放弃当前草稿或当前 review 结果 | 结束当前流程且不保留正式对象 |
| `commit` | 把草稿对象正式写入长期存储 | 让对象从临时态变成正式态 |
| `reindex` | 对索引和地图做重建或更新 | 让新内容进入可检索状态 |
| `synthesis` | 把多条相关内容综合成总结、回答或新对象 | 负责“归纳与整合” |
| `taxonomy` | 受控词表层 | 统一领域词、方法词、项目词和别名 |

## 3. `IPK` 内容系统术语

### 3.1 核心对象

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `piece` | `IPK` 里的统一最小长期内容对象 | 承载一条可以被长期保存和再次调用的内容 |
| `piece.md` | `piece` 的正文文件 | 保存真实内容、细节、推导、反思和证据 |
| `meta.json` | `piece` 的结构身份证 | 保存 `id`、类型、时间、来源、项目归属等稳定字段 |
| `surface.json` | 面向 AI 的工作面 | 让 AI 在不读正文时也能做判断、检索和联想 |
| `links.json` | `piece` 与其他 `piece` 的关系层 | 显式保存关系边，而不是只靠标签或隐含记忆 |
| `draft` | 入库前的工作草稿对象 | 承载 review、暂存、重写和编辑过程 |
| `draft_id` | 工作草稿的稳定标识 | 支撑暂存重开、编辑续接和统一 review 流 |
| `workspace_ref` | 来源工作区或目录身份引用 | 记录这条内容来自哪个工作区，而不是它属于哪个概念项目 |

### 3.2 `surface` 相关术语

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `surface` | `piece` 暴露给 AI 的结构化工作面 | 让 AI 低成本判断“值不值得继续深入” |
| `human` | `surface` 里面向人的一层 | 提供 `body_summary` 给用户审核 |
| `body_summary` | 给用户看的正文简介 | 帮用户快速确认这条 `piece` 是否表达对了 |
| `catalog` | `surface` 的首轮筛选层 | 供地图编译、轻量列表和第一轮筛选使用 |
| `catalog.summary` | 给地图和路由看的精简摘要 | 告诉系统这条 `piece` 大致在讲什么 |
| `retrieve` | `surface` 的精确检索层 | 判断这条内容是否和当前问题强相关 |
| `associate` | `surface` 的弱联想层 | 支持类比、桥接、方法迁移和扩展联想 |
| `role` | `retrieve` 里描述这条 `piece` 在回答中的角色 | 区分它更像证据、背景、方法还是启发 |
| `retrieval_hints` | 有助于召回该 `piece` 的提示表达 | 提高不同提问方式下的召回率 |
| `association_hints` | 有助于做弱连接扩展的提示 | 让系统能从相似结构里得到启发 |
| `salience` | 一条 `piece` 的整体显著性估计 | 帮助排序和地图编译 |

### 3.3 关系与导航术语

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `links` | `piece` 之间的结构化关系边 | 告诉系统哪些内容相互支持、延伸、矛盾或共享方法 |
| `link reason` | 一条关系边的原因说明 | 防止关系图变成噪音 |
| `map` | 从大量 `piece` 上方编译出的导航层 | 告诉 AI 先去哪里看 |
| `maps` | 不同维度、不同层级的地图集合 | 共同构成多层导航系统 |
| `navigation` | 基于地图逐层下潜、切换视角的过程 | 替代一步到位的全库搜索 |
| `by_project` | 按项目组织的地图或索引 | 帮助回顾某个项目积累了什么 |
| `by_time` | 按时间组织的地图或索引 | 帮助看某段时期发生了什么 |
| `by_domain` | 按领域组织的地图或索引 | 帮助从学科视角进入内容库 |
| `by_method` | 按方法组织的地图或索引 | 帮助找“问题不同但方法相似”的内容 |
| `open_questions` | 未解决问题视图 | 帮助复盘、规划和长期追踪 |
| `graph_links` | 关系网络视图 | 帮助做关系扩展和联想 |

### 3.4 运行时术语

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `route` | 运行时选地图、选路径的动作 | 决定从哪个入口开始查 |
| `retrieve` | 运行时按精确相关性收缩候选的阶段 | 找强命中内容 |
| `associate` | 运行时做弱联想扩展的阶段 | 找启发、类比和桥接方向 |
| `body access` | 继续读取 `piece.md` 正文的动作 | 获取最终细节与证据 |
| `synthesis` | 把命中的内容综合成回答、综述或新 `piece` | 形成高层结论和再利用结果 |

### 3.5 `piece` 生成链路术语

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `select` | 从原始输入中决定哪些内容值得入库 | 控制入口 |
| `capture` | 提取原始内容、上下文和来源信息 | 为后续生成做准备 |
| `draft` | 生成标题、简介和正文草稿 | 形成初始内容层 |
| `structure` | 生成 `meta`、`surface` 和 `links` | 形成结构层 |
| `quality` | 对关键字段做质量重写和自查 | 提高结构层和工作面的判断力 |
| `review` | 用户审核标题、简介和正文 | 控制表达准确性 |
| `commit` | 正式写入 `piece` | 把草稿对象转成长期对象 |
| `reindex` | 更新 indexes 和 maps | 让新内容进入路由系统 |
| `edit-start` | 从已入库 piece 启动编辑工作草稿的动作 | 先转成工作 draft，再进入统一 review 流 |

### 3.6 读模型与 UI 术语

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `DraftView` | 面向 review、暂存重开和编辑的读模型 | 给前端弹窗一个稳定可展示对象 |
| `PieceCard` | 面向列表和轻量展示的读模型 | 给 `编辑pieces`、列表和卡片使用 |
| `SearchHit` | 面向 `搜索` 结果的读模型 | 承载搜索命中对象的展示与排序信息 |
| `AssociateHit` | 面向 `联想` 结果的读模型 | 承载弱连接结果的展示与控制信息 |

## 4. 用户自适应系统术语

### 4.1 核心对象

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `signal` | 单次会话中的局部证据 | 表示“这次互动里看到了什么倾向或事实” |
| `summary` | 一段时间内对 signals 的趋势压缩 | 把零散证据变成稳定趋势 |
| `proposal` | 高影响候选结论 | 在进入长期层前作为待确认缓冲，并支持同类合并与统一审阅 |
| `confirmed record` | 已确认、可长期生效的记录 | 构成长效理解层 |
| `global_guidance` | 工作区 global 侧的 guidance 对象 | 保存轻量背景 + refs，帮助 session 缩小候选范围 |
| `subject_profile` | 某个学科或主题内的长期理解 | 保存知识坐标、规范偏好和学科内理解方式 |
| `task_scope` | 某个长期逻辑任务的状态和习惯层 | 保存任务目标、进度、局部习惯和约束 |
| `artifact_contract` | 某类产物的输出和更新规则 | 保存“写成什么样、写到哪里、是否联动更新” |
| `policy` | 面向未来运行时的策略层 | 决定未来应该怎么回答和怎么执行 |
| `context_packet` | 运行时真正送入模型的小而准上下文包 | 把长期理解压缩成可用上下文 |
| `context compiler` | 运行时上下文编译器 | 从多层记录中选出少量相关内容，并编译成 `context_packet` |
| `scope matching` | 判断当前请求、证据、会话或行动属于哪些长期作用域 | 决定当前应关联哪些 project、task_scope、subject 或 artifact |
| `scope read` | 运行时读取相关作用域记录 | 决定这轮应该把哪些习惯编译进 `context_packet` |
| `scope promotion` | 把低层习惯提升到更高层级的传递机制 | 决定一条局部习惯是否应通过 proposal 成为更广范围的长期规则 |
| `summary window` | 对一段时间或多次会话中的 signals 做阶段压缩的窗口 | 防止单条证据直接改写长期层 |
| `session binding` | 当前 session 的实际挂载状态卡片 | 记录当前 session 绑定到哪个 initiative / task_scope / subject / artifact，以及哪些 habit 已确认生效 |
| `artifact bundle` | 一组需要一起维护的 artifact | 表示 overview/details 等成对或成组更新关系 |

### 4.2 策略相关术语

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `response policy` | 回答策略 | 决定怎么解释、从哪里开始、讲到多深 |
| `operation policy` | 执行策略 | 决定怎么做事、先做什么、更新哪些目标 |
| `resource preferences` | 资源使用偏好 | 决定优先用哪个目录、工具、程序或资料来源 |

### 4.3 作用域相关术语

| 术语 | 在项目中的意思 | 它主要负责什么 |
| --- | --- | --- |
| `global` | 全局层作用域 | 适用于跨任务成立的长期规律 |
| `subject` | 学科或主题层作用域 | 适用于某一学科或主题内成立的规律 |
| `task_scope` | 长期任务层作用域 | 适用于某个持续任务内部的状态和习惯 |
| `artifact` | 具体产物层作用域 | 适用于某类具体输出对象的规则 |
| `session` | 当前会话层作用域 | 只对这次对话临时有效的要求 |

### 4.4 慢更新链路术语

这条链在文档里经常出现：

```text
会话证据
  -> signals
  -> summaries
  -> proposals
  -> confirmed records
  -> runtime context
```

它可以这样理解：

- `signals`
  是局部观察
- `summaries`
  是阶段压缩
- `proposals`
  是待确认候选结论
- `confirmed records`
  是正式长期层
- `runtime context`
  是运行时真正拿去用的压缩上下文

这条链的目的，是防止单次会话里的高影响判断直接静默生效。

## 5. 最容易混淆的几组词

### 5.1 `piece` 和 `skill`

- `piece` 是内容对象
- `skill` 是方法或工作流协议

最简理解：

- `piece` 回答“存什么”
- `skill` 回答“怎么找、怎么想、怎么做”

### 5.2 `body_summary` 和 `catalog.summary`

- `body_summary` 是给用户审核的自然语言简介
- `catalog.summary` 是给地图和路由用的精简摘要

前者偏人类阅读，后者偏 AI 路由。

### 5.3 `retrieve` 和 `associate`

- `retrieve` 负责强相关判断
- `associate` 负责弱连接扩展

最简理解：

- `retrieve` 问“这条是不是我要找的”
- `associate` 问“这条能不能带来有价值的启发”

### 5.4 `links` 和 `map`

- `links` 是对象之间的关系边
- `map` 是由大量对象和索引编译出来的导航入口层

最简理解：

- `links` 回答“谁和谁有关系”
- `map` 回答“先去哪看”

### 5.5 `profile` 和 `policy`

- `profile` 是系统对用户和任务的长期理解
- `policy` 是基于这种理解导出的未来动作策略

最简理解：

- `profile` 回答“系统知道了什么”
- `policy` 回答“因此之后该怎么做”

### 5.6 `summary` 和 `synthesis`

- `summary` 更像压缩已有内容
- `synthesis` 更像把多条内容综合成新的高层结果

最简理解：

- `summary` 偏“缩短”
- `synthesis` 偏“整合”

## 6. 如果只记住最关键的十个词

如果需要最小记忆集，建议先记住这十个：

1. `piece`
   `IPK` 的最小长期内容对象
2. `surface`
   `piece` 暴露给 AI 的工作面
3. `catalog`
   给地图和首轮筛选用的简层
4. `retrieve`
   给精确判断用的强相关层
5. `associate`
   给弱联想和迁移扩展用的层
6. `links`
   `piece` 之间的显式关系边
7. `map`
   从大量 `piece` 上方编译出的导航层
8. `signal`
   单次会话中的局部证据
9. `proposal`
   高影响候选结论，进入长期层前的确认缓冲
10. `policy`
   系统在未来回答与执行时的策略层

---

## 7. 一句话总结

这套文档里的专有名词，大多不是为了“显得专业”，而是为了把系统中的不同职责明确拆开。

只要抓住下面这条主线，绝大多数词都会变得容易理解：

- `IPK` 内容系统负责“存什么内容，以及怎么找这些内容”
- 用户自适应系统负责“系统怎样理解用户，以及未来怎么更合适地使用这些内容”
