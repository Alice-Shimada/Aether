# 用户自适应系统愿景记录

## 1. 这套系统现在到底想做什么

这套系统的目标，已经不再只是“让 AI 更懂用户偏好”。

它现在更准确的目标是：

- 让 AI 在长期交流中逐渐理解用户
- 让 AI 在不同学科里理解用户的知识坐标与常用规范
- 让 AI 在某个具体任务里理解当前目标、上下文、已完成工作和未解决问题
- 让 AI 在需要产出文件时理解对应格式与写作约束
- 让 AI 在长期任务里理解用户的工作顺序、记录习惯、工具偏好与操作方式
- 让 AI 能把低层 session 中观察到的习惯，经过证据、合并和确认后，提升到更合适的长期作用域
- 让这些理解真正进入后续回答、总结、文件写入和执行动作

因此，这套系统更像一个：

- 长期用户理解系统
- 长期任务理解系统
- 长期产物约束系统
- 最终面向回答与执行的上下文编译系统

## 2. 为什么它必须这样设计

### 2.1 AI 常常懂知识，但不懂具体的人

AI 可能知道大量物理和数学内容，但它往往不知道：

- 用户已经会什么
- 用户在哪个学科里更熟，在哪个学科里还在过渡
- 用户习惯哪套理论语言或记号
- 用户在学习场景和研究场景中偏好是否不同
- 用户在某个具体任务里到底已经做到哪一步了

于是回答很容易：

- 过浅
- 过深
- 切到陌生规范
- 忽略当前任务上下文
- 以及在需要真正动手工作时，选错工具、路径或操作方式

### 2.2 用户决定习惯边界，AI 不要求用户管理底层

这次讨论里已经对齐了一个非常关键的原则：

> 用户决定哪些习惯值得固定、适合在哪些范围生效，以及何时提升、收窄、禁用或纠正。  
> AI 负责内部表示、存储、提取、检索、编译、关系维护和运行时调用。

原因很直接：

- 用户不一定是 AI 专家
- 用户不应该被迫理解 embedding、schema、索引和检索策略
- AI 最了解怎样让未来的 AI 更高效地读取这些记录
- 但用户最了解自己的习惯，所以作用范围和高影响规则不能完全交给 AI 静默决定

所以这套系统必须把“怎样存、怎样搜、怎样组织”尽量变成 AI 的责任，而不是用户的负担。

### 2.3 长期理解必须分层，而不是混在一张画像里

一个用户可能同时拥有：

- 全局的表达与学习风格
- 只在某个学科里成立的知识坐标
- 只在某个项目里成立的任务状态
- 只对某个具体文件成立的格式约束

如果把这些都塞进同一个 profile，就会非常混乱。

因此系统必须至少分出几层作用域（习惯库五层平行 scope，详见 [user-adaptation-system-top-level-constraint.zh-CN.md](/home/bzz/Aether/docs/IPK/02-user-adaptation-system/user-adaptation-system-top-level-constraint.zh-CN.md)）：

- `global`
- `subject`
- `initiative`
- `task_scope`
- `artifact`

注意：`project` 是 Aether 工作区对象，不是习惯库 scope；`session` 是运行时层，不是习惯库 scope。这两者与上面五层身份独立。

### 2.4 高影响理解不能只靠自动猜测

有些内容一旦判断错，会明显影响后续工作质量。

例如：

- “用户只想管物理内容，不想管 AI 底层实现”
- “这门课的总结默认写进哪一个 LaTeX 文件”
- “这篇论文里优先突出什么，不突出什么”
- “这个任务里默认维护 overview 和 details 两份记录文件”
- “有多个等价工具时优先复用 project 内已有资源”

这类内容不适合直接静默写入长期策略。  
更合理的方式是：

- AI 从多次对话里自动提炼候选结论
- 把高影响结论整理成 `proposal`
- 对同类 `proposal` 做合并和去重
- 放入待处理队列，在合适时机让用户统一确认
- 确认后再进入稳定层

## 3. 这套系统的核心原则

### 3.1 用户负责习惯边界，不负责底层结构

用户应该主要负责：

- 提问题
- 做研究
- 读材料
- 提纠正
- 决定高影响习惯是否成立
- 决定习惯适合的作用范围
- 决定是否提升、收窄、禁用或改写习惯
- 确认关键总结是否准确

用户不应该负责：

- 定义内部 schema
- 设计检索结构
- 决定用 markdown 还是 json 作为内部主记录
- 调 embedding 参数
- 管理 AI 怎样组合上下文

### 3.2 默认本地优先

这套系统涉及：

- 用户的长期风格
- 用户的知识短板与熟悉区
- 用户的研究或学习任务状态
- 具体文件与写作偏好

这些都具有较强隐私性。

因此当前设计明确倾向：

- 记录默认保存在用户本地
- 不默认上传云端
- project 引用层记录默认保存在独立 memory root 的 `projects/` 分区
- global 真源记录默认保存在同一个独立 memory root 的 `global/` 分区
- subject 真源记录默认保存在同一个独立 memory root 的 `subjects/` 分区
- task_scope / artifact 真源记录默认分别保存在 `task-scopes/` 和 `artifacts/` 分区
- 第一版不默认把长期 adaptation 真源写入项目目录

### 3.3 适配不是盲目迎合

系统的目标不是“越来越像用户的即时要求”，而是：

- 理解用户
- 配合用户
- 保持稳定
- 在需要时适度纠偏

### 3.4 记录要适合 AI，也要可被人审阅

最终记录不应该只是一堆 AI 私有黑盒。

更合理的方式是：

- 用结构化记录做稳定读写
- 用人类可读摘要做审阅和确认
- 把同类待确认判断合并后再给用户统一处理
- 让用户在必要时只需要回答“对不对”

## 4. 当前最关键的架构结论

当前最关键的设计结论已经变成：

```text
会话证据
  -> signals
  -> summaries
  -> promotion candidates / proposals
  -> confirmed records
     (global / subject / initiative / task_scope / artifact)
  -> context compiler
  -> 后续回答 / 总结 / 文件写入
```

这里最重要的不是某一个对象，而是两件事：

### 4.1 记录必须分作用域

- `global` 负责用户全局风格
- `subject` 负责学科知识坐标
- `initiative` 负责长期事项级背景、约束和跨任务规则；v1 与 Aether 工作区 project 完全解绑，initiative 归属由路由 classifier 决定（详见 [docs/decisions/project-initiative-decoupling-and-routing.md](../decisions/project-initiative-decoupling-and-routing.md)）
- `task_scope` 负责具体任务的持续上下文
- `artifact` 负责具体产物的输出约束

### 4.1a 低层习惯需要可审阅地提升

大多数习惯证据会先出现在 session 里。系统可以自动记录这些局部证据，也可以自动形成 promotion candidate，但不能静默扩大作用域。

当某个局部习惯可能应该进入 `task_scope`、`initiative`、`subject` 或 `global` 层时，它应进入 proposal 队列，让用户看到来源证据、目标作用域和未来影响后再确认。`workflow_profile` 若未来引入，应单列为 vNext。

### 4.2 真正影响回答的是 context compiler

不是把所有记录都一股脑喂给 AI。  
而是在每一轮请求前，根据当前问题，自动选择并编译少量最相关的记录。

### 4.3 真正影响执行的是 operation policy

系统最终不应只知道“怎样讲”，还应知道：

- 先做什么
- 该更新哪些记录文件
- 该优先调用哪个工具、目录或程序
- 应怎样组织这次操作

## 5. 这套系统最终希望带来的体验

### 5.1 问新知识时，AI 更知道从哪里讲

它会尽量知道：

- 你已经会哪些 anchor
- 你习惯哪套规范
- 应不应该从熟悉语言切入

### 5.2 做长期任务时，AI 更知道你现在在做什么

它会尽量知道：

- 这个任务的目标
- 你已经完成了什么
- 最近形成了哪些结论
- 还有哪些 open questions

### 5.3 要求“总结并记录”时，AI 更接近直接完成工作

它不只会总结聊天内容。  
它还会尽量知道：

- 该突出什么
- 该省略什么
- 应该写成什么格式
- 应该写进哪个文件、哪个位置

### 5.4 做执行型任务时，AI 更像一个熟悉你习惯的助手

它会尽量知道：

- 你习惯的工作顺序
- 你是否维护成对的记录文件
- 同类工具里更常用哪一个
- 在这个 task_scope 中应怎样调用这些资源

## 6. 当前一句话总结

用户自适应系统现在最准确的一句话，不是：

- “让 AI 记住用户偏好”

而是：

- “让 AI 在长期交流中逐渐形成对用户、学科、任务和产物的分层理解，并把这种理解编译进未来回答与执行。”
