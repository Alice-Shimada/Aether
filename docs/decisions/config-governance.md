# 配置变更记录规则

## 已确认决定

- 从现在起，本项目所有配置变更都必须同步写入 `docs/decisions/` 下对应的 Markdown 文件。
- 不能只在对话里说明配置改了什么；文档更新本身是配置变更的一部分。
- 如果还没有合适的决策文件，先在 `docs/decisions/` 新建对应主题文档，再实施配置变更。

## 适用范围

- 项目级、用户级、环境级、构建级、部署级配置。
- `.json`、`.jsonc`、`.toml`、`.yaml`、`.yml`、`.env` 模板、CLI 配置、运行时开关、特性开关、权限策略、默认值调整。
- 任何会改变系统行为、默认路径、发现顺序、加载方式、开关语义或运维方式的配置改动。

## 文档要求

- 记录变更背景：为什么要改。
- 记录最终规则：现在系统应如何配置。
- 记录影响范围：会影响哪些模块、环境或用户。
- 记录迁移或兼容性信息：旧配置是否还支持，是否需要迁移。
- 记录验证方式：如何确认配置改动已按预期生效。

## 执行约定

- 配置变更与对应文档更新应在同一次任务中完成。
- 优先复用已有决策文档；只有在主题不匹配时才新增文件。
- 如果实现过程中配置方案发生变化，先更新 `docs/decisions/` 中的文档，再继续修改代码或配置。
- 没有文档落点的配置改动，不算完成。

## 文件组织

- `docs/decisions/` 用于存放已确认、可执行、应长期维护的配置决策。
- 文件名应按主题命名，例如 `config-governance.md`、`provider-config.md`、`build-config.md`。
- 未决项、待讨论项、豁免条件放到 `docs/decisions/open-questions.md`，不要混进已确认决策。
